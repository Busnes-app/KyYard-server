# Web

## Purpose
React 19 + TypeScript + Vite PWA for fleet operations, provider sign-in, recovery and administration.

## Ownership
Owns user interface components, service worker caching, PWA installation manifests, and frontend theme switching.

## Local Contracts
- Login consumes the opaque `#sso-mfa=` challenge into component memory, removes the fragment from history immediately, and uses the existing TOTP/recovery-code form before authenticating linked local SSO accounts.
- Settings → Sign-in offers `AccountSSO` to connect an enabled provider to the current local account. It asks for the current KyYard password, clears the input before every request, starts the CSRF-bearing link flow and follows only an HTTPS authorization URL. Provider login completes on the original account session; the success redirect opens Sign-in with a status message. Provider configuration remains platform-admin-only.
- `KubernetesNetworking` is the on-demand Internal networking panel on mapped cluster applications: read the selected latest revision and endpoint inventory, edit per-service IPs (25 rows/page), save a networking-only revision under `application.edit` with CSRF and expected head, and refresh Applications after success. Unknown/conflicting writes stay blocked across closing/reopening. Show last-reported owned Service backend URLs separately from requested addresses; HTTP is an explicit backend assumption, IPv6 URLs are bracketed. Plans and historical revisions display requested IPs. Fixed messages cover unavailable/immutable/in-use addresses and old agents.
- Web themes default to the Busnes.app cream/light and charcoal/dark palettes with orange accents, following the OS until a browser-local choice is saved. Preserve existing named themes and saved choices.
- Adopted configuration offers on-demand Deployment preflight with 25 services/page, full reported image/target IDs and fixed blocker messages under the heading "Deployment preflight". When `executable` is true it says "Ready to plan: every service maps to an adopted container and its image is known on the host." instead of the blocker list; when it is false with no top-level blockers (only per-service findings) it says "Not ready to plan." Each service row lists its resolved mounts and, under "Will be dropped by the recreate:", the mapped container's mounts the recreate leaves off, and under "Cannot be recreated:" its `unsupported_mounts`; `bind_mount_new`, `mounts_unreported`, `mount_unsupported` and `volume_missing` are fixed texts in `messages`. `clock_skew` and the plan-time blockers (`inspection_unavailable`, `replacement_identity_changed`, `configuration_unsupported`, `frame_too_large`, `too_many_registry_hosts`, `frame_invalid`, `agent_deploy_unsupported`, `agent_pull_unsupported`, `agent_inspect_unsupported`) are fixed texts in `messages`. The live inspection dialog shows "Configuration: fully expressible" or the unsupported configuration by human name from `unsupportedNames` (`ApplicationInspection.tsx`); a code outside that table, a disagreeing `configuration_verified` or a missing `unsupported` list refuses the whole observation. `MountList` (`ApplicationPreflight.tsx`) is the one mount renderer (revision, preflight, plan): kind label `volume`/`bind` from a fixed table (anything else "other"), `source → target` as text, `ro` badge. Mapped services offer a single native modal live inspection using the authorized endpoint API. Compare container/image/creation identity to the preflight target; display only validated redacted facts, discard results on close/scope refresh, abort dismissed requests and never retry automatically. Keep running-container image separate from desired image; selected facts do not establish configuration parity. IDs are observations, not deployment pins; port checks cannot detect host processes or unreported bindings. Hide observations if the selected adoption changed. No apply action.
- Adopted configuration offers an on-demand Deployment plan panel (`ApplicationDeploymentPlan.tsx`), gated on the deployments read alone; only the plan form beneath it additionally gates on the mapping read. Typed project confirmation posts instance/mapping-version/revision to mint a plan, 25 services/page showing pinned image ID and repository digest (or "No repository digest reported"), or for a service the apply pulls only "pulls " + 12 hex characters of `pull_digest` (never the image it replaces), replaced container/image identity, each service's mounts and secret reference counts only; "Volumes to ensure:" lists the plan's resolved host volume names. A `Revision to plan` selector offers `latest_revision..1` (default latest) and posts the chosen `revision`; below latest it shows the fixed reapply warning (own saved environment values, data written since not reversed, mapping reviewed against the latest). A `remove` row's plan renders its container list (service, name, container ID) instead of the services table; its progress uses the same polling and result section, and a denied removal precondition advises refreshing the inventory and re-adopting a container recreated outside KyYard rather than planning again. An application with no instance (removed or released) offers a read-only "Deployment history" toggle (`ApplicationHistory`) listing all its rows. `knownBlockers` (`ApplicationPreflight.tsx`) is the one parser for a 409 `blockers` list. `409` blockers map through the shared preflight `messages`; any other blocked/unknown outcome disables re-planning until refresh. A 409 also lists `serviceFindings`: per named service (service grammar only) its unsupported configuration by human name, or "no live inspection answered". A `recheck` denial is explained like a precondition keyed on its step code; a `clock_skew` result explains the host clock (see the Apply deployment bullet for the outcome-code mechanism).
- A mapped instance (`mapping_version >= 1`) shows an "Updates" toggle (`ApplicationUpdates.tsx`) between preflight and the deployment plan; like its siblings it requests nothing until opened. Open, it reads `GET .../applications/{app}/updates` (rows only when `instance_id` matches the instance; "No update check yet." when empty) and "Check for updates" posts `POST .../updates/check`, then re-reads, keeping the previous rows on screen until the read lands. When any shown row is `update_available`, a typed project confirmation (`project` prop) enables "Plan update", which posts `POST .../deployments` `{instance_id, mapping_version (from the check), revision (latestRevision prop), confirm, update: [those services]}`; success shows "Plan created; review it in the deployment plan panel." and calls `onPlanned`, which `Applications.tsx` turns into a `refreshKey` bump that remounts the open plan panel. Refresh applications before planning."), 409 `deployment_in_progress` ("A deployment is being applied; wait for it to finish.") and 409 `check_in_progress` ("An update check or update plan is already running.") have fixed texts; anything else shows one fixed refusal text. No apply action here.

A pause the validation loop caused is explained by `pauseText`. The deployment plan's result shows the same `ValidationLine`.
- A `planned`, unexpired plan offers "Apply deployment": a second typed confirmation naming the application, revision and endpoint states that containers will be replaced and nothing rolls back. On `202` the panel polls `GET .../deployments` directly (not through the shared resource, so the loop owns its failure count, deadline and pause notice) every 5 s while state is `applying`, until three minutes past the row's `deadline` (15 minutes from the first tick when it has none) or 3 consecutive fetch failures, then shows "Status updates paused; refresh to continue." The panel's "Current revision · previous" line reads the instance, so a polled row reaching `succeeded`, and "Refresh plan", call `onChanged`, which `Applications.tsx` wires to `instances.reload`. A settled row shows state, its correlation ID ("search the audit log for it"; a planned row shows it under the plan), the row detail only when it is one of the server's own sentences (`SERVER_DETAILS`: connection ended, no result arrived, the host's result did not match, the endpoint disconnected before the deployment or removal was sent), the result code's text (`RESULT_CODES`), a 25-row step table (service, step, outcome, `stepText`: the step code's text from `STEP_CODES`, with `unsupported` codes named through `unsupportedNames` and unknown ones dropped, a 64-hex container ID for `identity_unreadable`/`identity_unverified` and a 3-digit status for `runtime_status`, each rendered only in that shape) and the new container identities. `legacy` reads "The agent did not classify this outcome; upgrade the agent."; any other unknown code renders as the inert text ``unrecognised outcome `<code>` ``. Explanations key on the row state first: `unknown` (host may or may not have acted), `timed_out`, and `failed` with no result (never sent to the host); a `clock_skew` result; then on the failing step's code: `denied` at `precondition` or `recheck` (`configuration_drift`, `container_missing`, `identity_mismatch`, `image_missing`, `legacy` says nothing more, otherwise configuration the definition cannot describe), `pinned_image_missing`, and `failed` (previous container renamed `.kyyard-prev-<id>` on the host). The panel states that planning executes nothing; it does not call an applyable plan inert. `501`, `403` and named `409` codes (`deployment_in_progress`, `adoption_changed`, `endpoint_offline`, `deployment_not_sent`) map to fixed messages; error bodies are never rendered. No retry, no rollback control.
