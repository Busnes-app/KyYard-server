# Pull Step and Controlled Recreate Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let an operator take a detected image update deliberately: a plan pins the registry's current digest for chosen services, the agent pulls that digest with the credential carried in the frame, verifies the pull, and only then runs the existing replacement.

**Architecture:** The wire gains a `pull` per service and a per-host `registries` map on the frame (Task 1). The adapter gains a `pull` step between `precondition` and `rename` (Task 2). The store's plan does fresh `Head` resolves for the `update` list and pins `pull_reference`/`pull_digest`; apply builds the `registries` map inside the apply transaction; settle accepts a pulled identity only with the pinned digest (Task 3). The API adds the server-wide cap and passes the resolver into planning; the agent's ledger is proven credential-free (Task 4). The UI gains "Plan update" (Task 5). Docs close M7a (Task 6).

**Tech Stack:** Go (`database/sql`, SQLite + PostgreSQL, `net/http` Engine API client), `internal/registry`, React 19 + TypeScript + Vitest.

**Spec:** `docs/superpowers/specs/2026-09-23-pull-step-design.md`

## Global Constraints

- Wire constants: `MaxDeploymentRequestBytes = 320 << 10`, `MaxRegistryAuthHosts = 16`, `MaxRegistryAuthSecretBytes = 4096`; `StepPull = "pull"`; step order per pulled service `precondition, pull, rename, create, stop, start, remove`; `image` only for services without a pull.
- `DeploymentService.Pull != nil` ⇒ `ImageID == ""`; otherwise `ImageID` full. `Pull.Reference` = `<host>/<repository>@<digest>` and `Pull.Digest` equals that digest. Every `Registries` key is a host some `Pull.Reference` names; secrets non-empty, ≤ 4096 bytes, UTF-8, no NUL.
- Result identity of a pulled service: full `ImageID` and `ImageDigest == Pull.Digest`; settle refuses anything else with `ErrInvalid`.
- Credentials: decrypted only inside the authorized operation (plan `Head`: `application.deploy`; apply frame assembly: `application.deploy`); in server memory only for the resolve phase or the frame; never in `deployments.plan`, `deployments.result`, audit rows, error strings, logs, the agent ledger or a result detail.
- Plan blockers, exact names: `update_not_mapped`, `registry_not_configured`, `registry_unauthorized`, `registry_not_found`, `registry_rate_limited`, `registry_private_destination`, `registry_unavailable`.
- Plan `Head` resolves: at most 4 concurrent, 60 s overall, outside any transaction; the audited write re-checks mapping version, latest revision and container/image pairs (`ErrAdoptionChanged`).
- Adapter step details are fixed text: `pull failed`, `unauthorized`, `not found`, `pulled image does not match`; never daemon text.
- Server-wide cap: 4 registry operations (update checks + plan resolves) in flight; over it 429 code `too_many_checks`, text `Too many registry checks are running; try again in a moment`.
- `DeploymentApplyDeadline` unchanged (10 min).
- Every store behaviour tested on SQLite and PostgreSQL. Commit trailer: `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`.

## Review Focus

1. A frame whose `registries` map names a host no service pulls from (a credential sent for nothing) must fail validation on both sides (Task 1 test).
2. A pulled image whose `RepoDigests` lists the digest under a different host spelling (`docker.io/library/alpine@…` vs `alpine@…`) must still verify; a digest for a different repository must not (Task 2 tests with both spellings).
3. A registry that returns 200 for the pull but the daemon's inspect reports another ID or no matching digest: the step must fail before rename (Task 2 test).
4. A plan minted with `update` for a service whose reference is already digest-pinned (`@sha256:`): pull that digest; no `Head` needed (Task 3 test).
5. A result for a pulled service that carries the old image ID and no digest (an agent that skipped the pull) must be refused at settle, leaving the row `applying` for the reconciler (Task 3 test).
