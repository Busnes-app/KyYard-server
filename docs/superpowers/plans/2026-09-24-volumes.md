# Volumes in the Application Definition Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let an application definition carry named volumes and bind mounts end to end, so a recreate keeps its data and deploy no longer refuses containers with mounts.

**Architecture:** The spec model and the importer learn `volumes` (Task 1). The inventory container and the wire learn mounts, and the adapter reports them, ensures named volumes, re-checks binds and mounts on create (Task 2). The store resolves host names, stores mapped containers' mounts, blocks new binds, and puts mounts and volumes in the plan and the frame (Task 3). Panels show volumes (Task 4). Docs close (Task 5).

**Tech Stack:** Go, yaml.v3 importer, Docker Engine API (`/containers/json` Mounts, `/volumes/create`, `HostConfig.Mounts`), SQLite + PostgreSQL, React 19 + Vitest.

**Spec:** `docs/superpowers/specs/2026-09-24-volumes-design.md`

## Global Constraints

- Model: `ApplicationVolume{Kind "named"|"bind", Source, Target, ReadOnly}` on the service; `DeclaredVolume{Name, External}` on the spec; ≤ 32 per service, ≤ 64 declared; named sources must be declared; bind sources absolute and clean (`path.Clean(s) == s`, no `..`); targets absolute, clean, unique per service; volume names `^[a-zA-Z0-9][a-zA-Z0-9_.-]{0,63}$`; no tmpfs, no anonymous volumes.
- Host name of a named volume: `Name` when `External`, else `<project>_<Name>`.
- Import: short syntax `SOURCE:TARGET[:ro|rw]` (leading `/` → bind; `./` or `~` → refused "write the absolute path"; bare target → refused "Anonymous volumes are unsupported; declare a named volume"; undeclared name → refused), long syntax `type: volume|bind`, `source`, `target`, `read_only` only; top-level `volumes:` accepts `name: {}`, `name:` and `name: {external: true}` only. Diagnostics carry line/column and no source text.
- Inventory: `Container.Mounts []Mount{Kind "volume"|"bind"|"other", Source, Target, ReadOnly}` (≤ 32; more → truncated and `MountsTruncated: true`).
- Blockers, exact names: `bind_mount_new`, `mounts_unreported`. Named volume differences never block; a dropped bind is allowed and listed as "will be dropped".
- Wire: `protocol.Mount{Kind "volume"|"bind", Source, Target, ReadOnly}`; `DeploymentService.Mounts` (≤ 32); `DeploymentRequest.Volumes []string` (≤ 64, each used by some service's volume mount); `StepVolume = "volume"`.
- Adapter: `undescribed` accepts mount types `volume` and `bind` only; precondition denies with detail `bind mount not present on the container` when a frame bind is missing on the old container; the `volume` step (phase one, before any replacement) does `POST /volumes/create` `{Name, Labels: {com.docker.compose.project, com.docker.compose.volume}}`, 201 succeeds (existing volumes included), else `volume create failed`; create passes `HostConfig.Mounts`, never `Binds`; removal never deletes volumes.
- Every store behaviour tested on SQLite and PostgreSQL. Commit trailer: `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`.

## Review Focus

1. A bind whose source differs only by a trailing slash or a symlink from the container's reported source must not be treated as identical by accident: compare cleaned strings exactly, and document that symlinks are compared as reported (Task 3 test with `/data/` vs `/data`).
2. A container with more than 32 mounts truncates the list; preflight must block with `mounts_unreported`, never silently compare a partial list (Task 2 protocol test + Task 3 test).
3. A named volume whose resolved host name collides with an external volume of the same name in another project: the recreate mounts by name, so two projects sharing `db_data` share data — the plan panel must show the resolved host name so an operator can see it (Task 4 test).
4. A `volume` step failure after some volumes were created leaves created volumes behind (harmless, namespaced); the deployment fails with nothing replaced (Task 2 test asserts no rename/create call).
5. Read-only binds: a definition marking a bind `ro` that the container has `rw` is a different mount (blocked as `bind_mount_new`), and the reverse too (Task 3 test).
