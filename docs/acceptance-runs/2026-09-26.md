## Notes per step

### 1. First start and credential

17:06 to 17:08. `docker compose up -d` from the stack directory; the bootstrap line
(`[SECURITY] Initial bootstrap: Created admin account. Username: admin | Password: …`) was found
in `docker compose logs kyyard` unaided. Sign-in led straight to "Change your password" (the

sign-in page; the new one landed on Containers with Local Docker `active` and the host's
containers listed. The proof-of-work check showed as "Security check verified." with no

### 2. Environment and enrollment

open it. The Hosts view is a pressed button under "Environment resources", not a tab control.
"Enroll a host" on this source build produced no command: a token, the note "Could not identify

The operator had to compose the `docker run` by hand (socket, identity volume, `--link`, plus the
test CA and `--add-host` this stage needs); the published image would have shown the one-line
command. Confusing moment for source builds only: the runbook prerequisites assume the
published image and the README covers `KY_AGENT_IMAGE`, so this is documentation, not a defect.
Each agent printed `agent key fingerprint: …`; Refresh hosts showed the row `pending` with the
truncated fingerprint; Approve is a native confirm dialog carrying the full fingerprint and
"Only approve if this matches the fingerprint the host printed." Both matched (b4c8fe99…c0f1,
0a68c13e…de20) and were compared before accepting. Both rows `active`. Each host page, Details,

Capabilities `container.exec, container.inspect, container.inspect.health,
container.inspect.verdict, deployment.apply, deployment.pull, deployment.remove`. Pass.

### 3. Containers, logs, terminal

17:13 to 17:17, host A, `acc-app-web-1`. The header Containers page and the endpoint page both
list containers with the search box "Search containers or images"; the Usage column reads
`cpu 0.0% · mem 16 MiB · 0 restarts`. Per-row actions sit inside a collapsed "Actions"
disclosure (Stop, Restart, Terminal, Logs, Remove disabled while running); the operator had to
open it first, which the runbook's "Actions, Logs" wording covers. Logs: the dialog "Logs for
acc-app-web-1" has "Filter logs" (placeholder "Search log text"), Timestamps, Load logs,
Follow / Stop following and a Download link; all worked, the download saved an 11-line file.
Restart: a native confirm naming host, endpoint and container ID; the row then reads
`container.restart: succeeded` and Activity lists `container.restart · <id> · succeeded`.
Terminal: Container user, Shell executable (`/bin/sh` prefilled), Confirm container name, "Open
terminal as chosen user"; "Connected. Terminal contents are not recorded."; `exit` gave "Process
exited with code 0." Pass on the runbook's checks, with two findings:

- **Log content missing with a misleading marker.** The container's log is 170 lines (1,387
  bytes on stdout, 8,797 on stderr). Load logs and the download showed only the 10 stdout
  lines followed by `--- kyyard <id>: 2342 bytes were dropped here because this reader was not
  keeping up ---`; no stderr line (nginx's `notice` lines) appeared. An operator would read
  this as lost output on an idle container. Under investigation; candidate release defect.
- **Stale inventory status that was not stale.** While the page stayed open across the
  Activity view, the status line read "Inventory generation 2, received 4m ago (stale: no
  report for over three minutes)" although the inventory API held generation 6 received
  seconds earlier; a reload showed "generation 7, received 32s ago". The status line does not

### 4. Read-only and cross-tenant

17:18 to 17:24. Prerequisites through Settings, Administration: users `reader` and `outsider`
(temporary passwords shown once in a field), organization "Acceptance B" with first
administrator `outsider`, reader added on the Members page by user ID as "read only". Both
accounts were forced through "Change your password" at first sign-in.

Reader on host A's `acc-app-web-1`: the Actions disclosure offers Stop, Restart, Logs, Remove
and no Terminal; Restart (after the same native confirm) answers `You do not have permission
for this action.` in the row; Logs opens the dialog and Load logs answers `KyYard: You do not
have permission to read logs.` with "No output loaded." The Applications and Registries checks
(environment variable names only; "credential set") wait for an application and a registry to
exist (steps 5 and 6) and are recorded there.

Outsider: `GET /api/organizations` lists only Acceptance B; its Environments page loads ("No
environments yet"). Direct `/organizations/org_initial` and
`/organizations/org_initial/endpoints/<host A>` render the page frame with "You do not have
access to this section. Ask an administrator for access." and no data (the endpoint ID in the
heading comes from the URL typed). `/api/organizations/org_initial/endpoints`,
`.../endpoints/<host A>/inventory`, `.../environments` and `.../audit` all answer 403
`tenant_access_denied`. No name, host or container of `org_initial` was visible. Pass.

Confusing moment: outsider's Containers home says "No hosts connected here yet. The standard
installation connects local Docker automatically; check Docker access if it is missing." Local
Docker belongs to the initial organization only, so a second organization's administrator is
told to check Docker access for a host that will never appear there. Wording candidate for the
Known gaps.

Root cause of the missing log content (confirmed 17:27): a container printing 100 numbered
lines at once (`seq 1 100`) showed 16 lines and `1020 bytes were dropped here because this
reader was not keeping up`. The agent's log reader hands each Docker frame to an 8-deep
outbound queue without waiting and counts the overflow as dropped
(`internal/agent/client/logs.go`, the `default:` branch), so any history request loses
everything after the first frames of the burst; stderr was only what happened to come later.
The wording blames a slow reader for what is a fixed-size queue. Release defect; fixed after
the run (see Defects). The stale status line is `EndpointPage` never refetching inventory
while open (`useTenantResource` fetches once); fixed in the same slice.

### 7. Disconnect, reconnect, revoke

Observations:
- The revoked host's page says "No inventory yet. It arrives with the agent's first report

- The revoked agent container is under `--restart unless-stopped`, so Docker restarts it every

### 9. Backup, drill, clean-install restore

With no key pinned the page led with "No backups are being made. Pair with KyRecovery or pin
the suite recovery key below." "Recovery key by hand": the scratch ceremony's public key,
Needed 2, Of 3, Pin key → "Recovery key Pinned 380edd80…31a21, 2 of 3 custodian cards open a
capsule". Back up now → "Capsule cap-KyYard-1790459153829609468 (112 KiB) written to
/data/backups/KyYard.cap-KyYard-1790459153829609468.kycap", Local copies 1 of 7, Download
capsule enabled. Run restore drill → "Restore drill passed 10 ms", checks "PRAGMA
integrity_check passed ok" and "Schema Version: data/ky_server.db — Database schema is version
35". The restore proper follows `docs/RESTORE.md` below.

RESTORE.md Steps 1 and 2 (17:48): the capsule copied out of `/data/backups`; `kyyard-server
restore -capsule /in.kycap -to /restored` run from the image as the current user with two
`ky2-…` shares pasted on stdin; it printed "Restored 6 files from capsule
cap-KyYard-1790459153829609468", service `KyYard (v1.0.0)`, created `2026-09-26T21:45:53Z`,
recovery key `380edd80…31a21` (the pinned key ID), payload hash `7e76fac9…`, "capsule schema
version 35; this binary migrates to 35". `find restored -type f -printf '%m %p'`: six files
at mode 600 (`config/settings.json`, `data/encryption.key`, `data/instance.key`,
`data/ky_server.db`, `data/recovery.pub`, `data/session.key`). Step 3: `docker compose down`
on the original (its named volume `acc_kyyard-data` kept), a fresh project `acc2` from the same
compose files plus `docker-compose.bind.yml`, `./data` empty, the restored `data/.` copied in
at mode 600, the same `KY_APP_URL`, `docker compose up -d`; the TLS proxy repointed at the new
container.

**Recovery outcome, Step 3 (17:47).** The restored server crash-looped with `Failed to load
configuration: session.key: keyfile: key path is not a regular file owned by the current user`.
Cause: RESTORE.md Step 1 runs the restore as the operator's own user (so the files "are owned by
you and not by root", line 136) and Step 3 copies them with `sudo cp -a`, which preserves that
ownership, while the container runs as root and refuses key files it does not own. Fixed here
with `chown -R 0:0` on the bind directory (through a throwaway container, this machine has no
sudo). The runbook needs `sudo chown -R root:root data` (or `cp` without `-a`) before
`docker compose up -d`. A step the custodians could not have followed as written: release
defect in the documentation, fixed after the run. After the chown the server started, and host
A's agent reconnected on its own within seconds (the log shows its settled deployment results
re-sent and ignored as late).

**Verification on the restored server (17:48 to 17:49).** Sign-in as admin with the replaced
password worked (the encryption key came back). Backup & recovery showed the same pinned key ID
`380edd80…31a21`, "Local copies 0 of 7" (the capsule directory is not part of a capsule; the
schedule kept its next run). Host A `active` without any action, host B still `revoked`. The
application listed revisions 1 and 2, "Current revision 2 · previous 1" and all three applies
in Deployment history. Check for updates answered "Up to date" for both services (the registry
path works; anonymous pulls survived). No command was in flight at the capsule moment, so the
`unknown` case was not exercised here (it was in step 7). Pass.

## Defects

- **D1, release defect, fixed in the follow-up PR.** The agent drops container log frames from an
  8-deep outbound queue during any burst and labels them "dropped because this reader was not
  keeping up"; a 100-line history request shows 16 lines. Fix: the log reader waits for the
  queue instead of dropping (it never carries heartbeats), and frames are gathered into chunks.
- **D2, fixed.** `EndpointPage` fetches the inventory once; the status line shows a growing
  "received N ago" and a false "stale" warning while the page stays open.
- **D3, fixed.** The deployment plan panel's "Current revision" line never refetches after an
  apply.
- **D4, fixed.** Not-found reads by the UI were audited as `failure` on `application.read` and
  `endpoint.read` (`readTenant` audited every error); a read's not-found now writes no row.
- **D5, release defect (documentation), fixed.** RESTORE.md Step 3 leaves the restored files
  owned by the operator; the container runs as root and refuses them. Add the chown.
