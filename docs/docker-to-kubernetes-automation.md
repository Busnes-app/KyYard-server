# Docker-to-Kubernetes automation: feasibility

Research date: 2026-09-27. This is a proposal and evidence note, not an implementation contract.

## What already exists

KyYard already deploys application definitions to enrolled Kubernetes endpoints: digest-pinned images, one-replica `Recreate` Deployments, ClusterIP Services, ConfigMaps, Secrets, optional single-service PVCs, ownership checks and rollout observation. It also analyzes Docker migrations and creates destination applications. Data copying, service-reference changes, application validation and traffic cutover remain operator tasks. Private image pulls require a namespace ServiceAccount imagePullSecret. See [README](../README.md#kubernetes-endpoints), [Kubernetes adapter contract](../internal/runtime/kubernetes/AGENTS.md), [renderer](../internal/runtime/kubernetes/render/render.go) and [migration checklist](../internal/migration/checklist.go).

The present renderer has no application probes, resource requests/limits or security context. Migration analysis can require acknowledgment of settings that will be dropped, and blocks host binds, shared volumes and several host-specific settings. Those are current product limits, not inherent Kubernetes limits. See [migration contract](../internal/migration/AGENTS.md) and [Kubernetes adapter contract](../internal/runtime/kubernetes/AGENTS.md).

## Kubernetes facts that constrain automation

- **Images can usually be reused.** Kubernetes accepts registry image references and immutable digests; destination nodes need access to a compatible image and any pull credentials. Creating Kubernetes objects does not transfer an image that exists only in a Docker daemon. [Kubernetes images](https://kubernetes.io/docs/concepts/containers/images/).
- **Compose conversion is only part of migration.** The official Kompose guide demonstrates generated Deployment/Service resources and warnings for unsupported Compose fields. Conversion does not establish application equivalence or move application data. [Kubernetes Compose translation guide](https://kubernetes.io/docs/tasks/configure-pod-container/translate-compose-kubernetes/).
- **Storage needs an explicit mapping.** PVCs request capacity, access modes and a storage class. `ReadWriteOnce` permits multiple pods on one node; it does not guarantee a single writer. Selecting a PVC therefore does not prove safe database concurrency. [Persistent volumes](https://kubernetes.io/docs/concepts/storage/persistent-volumes/).
- **External traffic needs a separate route.** ClusterIP is internal; external access requires a suitable Gateway/Ingress or Service exposure mechanism. A LoadBalancer Service also requires a load-balancer implementation. [Services](https://kubernetes.io/docs/concepts/services-networking/service/).
- **Running is not application readiness.** Readiness probes decide whether a container should receive traffic; startup probes allow slow initialization; liveness probes detect conditions requiring restart. Successful object creation is not proof of successful migration. [Container probes](https://kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes/).
- **Workload rollback does not rewind data.** Deployment rollback restores its Pod template. A StatefulSet supplies stable workload identity and storage attachment, rather than database backup or replication. [Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/), [StatefulSets](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/).
- **Database copying is application-specific.** PostgreSQL's ordinary filesystem backup requires server shutdown; a consistent snapshot is a distinct supported method. A generic tar stream of live database files is not sufficient. [PostgreSQL filesystem backup](https://www.postgresql.org/docs/current/backup-file.html).

## Proposed implementation scope

1. **Bounded stateless automation first.** Build on the existing analyzer and apply path. Persist a migration operation with source/destination identity, accepted mapping choices, exclusive execution, checkpoints, cancellation and recovery after agent/server disconnects. Validate image accessibility, namespace permissions, capacity/admission requirements and service references before applying. Begin with supported stateless applications and an explicit traffic target.
2. **Add application semantics to the definition and renderer.** Carry readiness/startup probes, resource settings and necessary security settings instead of silently dropping them. Record service-name mappings explicitly; avoid blind replacement of strings inside secrets or arbitrary configuration. Provision scoped image pull credentials when needed. These are extensions of the current model, not reasons to introduce a second manifest converter.
3. **Automate validation and traffic switching.** Test application behavior at the destination, then update an explicitly configured proxy, Gateway or DNS provider. Persist what changed so retry or reversal is deliberate. Retain the source until validation and cutover complete. DNS caches and background workers mean HTTP routing alone does not establish exclusive ownership of writes or jobs.
4. **Add stateful transfer as a separate capability.** Choose and size storage; create destination storage without starting application writers; quiesce the source or invoke a supported backup/export method; transfer through authenticated agents with bounded resources, progress, integrity checks and resumability; restore and validate before starting destination writers. The current agent contract needs narrowly scoped transfer/helper permissions and a durable operation lifecycle. Never resume the old source automatically after destination writes unless a defined reconciliation/restore method makes that safe.
5. **Prove failures on a real cluster.** Exercise private pulls, unschedulable pods, admission refusal, missing storage, interrupted transfers, permission loss, restart recovery, destination health failure and unsuccessful traffic switching. Prove source data survives failure and that retries cannot create competing writers. Existing fake-client tests and the opt-in real-cluster test are useful foundations, not evidence that this new workflow already works.

A safe initial feature is automated deployment and validation of supported stateless applications, with traffic cutover integrated for one chosen routing system. General stateful migration is a larger feature requiring application-specific consistency and recovery decisions; universal zero-downtime conversion should not be promised.
