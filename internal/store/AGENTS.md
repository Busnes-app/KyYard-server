# Storage Layer

## Purpose
Provides the unified Database Abstraction Layer (DAL) supporting pluggable backends (SQLite zero-CGO default and PostgreSQL enterprise) with automated dialect-aware migrations.

## Ownership
Owns data models, store interfaces (`UserStore`, `SessionStore`, `DeviceStore`, `GroupStore`, `AuditStore`, `SettingsStore`, `TenancyStore`), dialect translations, and schema migrations.

## Local Contracts
- `ReadInspectionTarget` uses endpoint.read and explicit scope to derive full container/image IDs and creation seconds from fresh complete Docker inventory. Require active endpoint, bounded valid snapshot and exactly one matching immutable ID. Re-read before publishing live inspection results; no successful-read audit, command or secret access.
- `PreflightApplication` is an application.read diagnostic over the latest digest-verified spec (the shared `preflight` takes a saved revision, 0 for latest; a missing one is `ErrNotFound`, and the head and mapping checks stay against the latest), confirmed mapping and fresh complete container inventory. Recheck instance/version/head and owned immutable identities across reads. Return endpoint ID and an optional validated inspection target derived only from the mapped owned container identity, independently of desired-image resolution. On the latest revision a binding to a service it does not define blocks as `unassigned_adopted_containers` and an unbound service as `service_unmapped`; a prior revision whose services are not exactly the mapped ones blocks once as `revision_services_differ`. `freshInventory` holds the inventory freshness rules (active endpoint, received within 3 minutes, observed within 5, complete and unique container list) shared with removal. A mapped service whose owned identity fails validation (not a full `sha256:` image ID with positive creation time) blocks as `replacement_identity_invalid`. Resolve exact local references only to full image IDs; incomplete/ambiguous image inventory cannot resolve. Report conservative published-port overlaps outside mapped replacements and within the definition. Each service's `mounts` is its volumes resolved (`resolveMounts`: `named` to kind `volume` with `VolumeHostName(preview project, declared)`, `bind` as written). On a mapped container whose mount list is missing (an agent older than mounts: every plan blocks until the agent is upgraded; the preview is rebuilt from live inventory, so the next report clears it) or truncated, the service blocks as `mounts_unreported`. Otherwise a definition bind with no identical container mount (kind, source, target and read-only by exact string, as reported: `/data/` is not `/data`, symlinks are not resolved) blocks as `bind_mount_new`; a container mount the agent refuses to replace (kind `other` such as tmpfs, or an anonymous volume, a 64-hex name) blocks as `mount_unsupported` and is listed in `unsupported_mounts`; any other container mount with no identical definition mount (read-only included, so a ro to rw change shows the old mount dropped) is in `dropped_mounts`, binds also in `dropped_binds`, and does not block. A service naming an `external` volume absent from the inventory's volume list, or while that list is truncated, blocks as `volume_missing`; project volumes are never checked (the agent creates them). External names stay in the plan's `volumes`; the blocker is what stops the agent creating one. `executable` is true exactly when no blocker (top-level or per service) remains; never resolve secrets, persist pins or dispatch commands. See docs/application-schema.md for inventory limitations. `clock_skew` (top level) when the inventory row's `observed_at` (agent clock) and `received_at` (server clock) differ by more than `protocol.MaxClockSkew`; `freshInventory`'s windows are unchanged.
- `PlanDeployment` (`application.deploy`) plans any saved revision (`PlanRequest.Revision`, 0 for latest) and mints a persisted plan only from a clean preflight (any blocker refuses with `PreflightBlockedError`); a mismatched instance/mapping version/revision/typed project is `ErrAdoptionChanged`. Migration 23's `deployments` table holds the plan; migration 24's `idx_deployments_live` allows one `planned` or `applying` row per instance, and a re-plan replaces a `planned` one inside the same locked transaction (refusing with `ErrDeploymentInProgress` while one is `applying`), with the JSON plan (pinned image IDs, single-match repository digests, replaced-container identity, restart, ports, sorted secret ref names, the preflight's resolved `mounts` per service, its `dropped_mounts` when non-empty (shown on the plan for approval), and `volumes`, the distinct volume host names in first-use order) capped at `MaxDeploymentPlanBytes`. `PlanDeployment(ctx, a, app, r, resolver, key, privateAllowed)`: every plan needs a 32-byte key (`ErrInvalid` otherwise); a plan without `r.Update` is that single locked transaction and needs no resolver. With `Update` (more than `protocol.MaxDeploymentServices` names, duplicates or a nil resolver are `ErrInvalid` before any audit) it runs the `CheckImageUpdates` phases under target `<app>/deployments/<id>`: read (`run`, no lock, no success row) drafts the plan (`draftPlan`), blocks `update_not_mapped` for a name that is not a service of the planned revision with a binding, `registry_not_configured` for a host with no row while anonymous pull is off, `registry_unavailable` for an unparsable reference, pins a digest reference directly with no registry call (it still needs a configured host or anonymous pull), and records `imageCheckStateOf`; resolve (`resolveImageChecks`, no transaction) maps errors to `registry_<detail>` blockers and a non-sha256 answer to `registry_unavailable`; write (`withTenantTargetDetails` on `context.WithoutCancel`) takes `lockApplication`, refuses a changed state with `ErrAdoptionChanged`, then refuses blockers or inserts (`insertPlan`) with details `pulls=N`. A pulled service records `pull_reference` (`registry.ParseReference` host + `/` + repository + `@` + digest, so `protocol.ImagePull.Host()` equals the registry row's host) and `pull_digest`; `image_id` stays the running image. `ApplyDeployment` sends it as `ImagePull{Reference, Digest, Tag}`, `Tag` being the spec reference in canonical form (`ParseReference` host + `/` + repository + `:` + tag; empty for a digest-pinned reference), and refuses (`ErrInvalid`, row stays `planned`) a frame larger than the `maxFrameBytes` the API passes for the endpoint (`protocol.MaxDeploymentRequestBytesLegacy` without `deployment.pull`). Once no other blocker remains, `checkFrame` builds the frame apply would send (`buildDeploymentFrame`, shared with apply: values and credentials decrypted in memory), measures it with `frameBlocker` against `PlanRequest.MaxFrameBytes` (set by the API from the endpoint's capabilities, `json:"-"`) and drops it: `too_many_registry_hosts` over 16 credentialed hosts, `frame_invalid` for any other `Validate` failure, `frame_too_large` past `min(MaxFrameBytes, 320 KiB)`. Nothing from the frame is stored. `ReadDeployment`/`ListDeployments` (`application.read`) carry `kind` and the endpoint's current name (joined at read, empty once the endpoint is gone) and compute `expired` from `DeploymentPlanTTL` (10 minutes) without rewriting state. `ReleaseApplication` locks the application row (same lock and order preflight uses for a plan) before checking; it deletes expired plan rows and refuses with `ErrDeploymentPlanned` while an unexpired one exists, and its live check and DELETE are scoped to organization, environment, application and instance under that lock, so a concurrent plan's uncommitted insert cannot be invisible to release on PostgreSQL. See docs/application-schema.md, Deployment plans. `draftPlan` reads `endpoint_capabilities` (`endpointCapabilities`) and `capabilityBlockers` adds `agent_deploy_unsupported` without `deployment.apply`, `agent_inspect_unsupported` without `container.inspect` or `container.inspect.verdict` (`inspectsVerdicts`), and, once pulls are pinned (the update path checks again after resolving), `agent_pull_unsupported` for a pulling plan without `deployment.pull`. Apply keeps its own 501s: capabilities can change between plan and apply. With both, and a preflight with no blockers of its own (`Executable`), every mapped service (one with an `InspectionTarget`) needs `PlanRequest.Inspections[containerID]` (`json:"-"`, set by the API): none is `inspection_unavailable`, a `Target` other than the preflight's is `replacement_identity_changed`, `ConfigurationVerified` false is `configuration_unsupported` with the codes on `PreflightService.Unsupported`. `PreflightBlockedError.Services` lists each service with blockers of its own as `BlockedService{name, blockers, unsupported}`. The inspections are consumed and never stored.
- `ApplyDeployment` (`application.deploy`, typed project confirm) locks the application row, then rechecks that the plan is `planned` (`ErrDeploymentInProgress` if already `applying`; a wrong confirm is `ErrInvalid`), unexpired, of kind `apply`, at a revision between 1 and the head with its stored spec digest, the instance's mapping version, an active endpoint and each replaced container's resource row; it builds the frame with `buildDeploymentFrame` (`IssuedAt` now; a service with `pull_digest` goes as `Pull` with an empty `ImageID`, and `Registries` holds `registryFor`'s credential, under the same key, once per pulled host that has one; a pulled host with no row while anonymous pull is off is `ErrAdoptionChanged`, row still planned) and refuses any `frameBlocker` finding with `ErrInvalid` before moving the row to `applying` by compare-and-set. The frame's per-service `Mounts` and its `Volumes` are the plan's, unchanged; spec and plan caps keep them far below the frame bound, which stays the guard. Values and registry credentials exist only in the returned request, never in a row or audit. `FailDeployment` marks an `applying` or `unknown` row failed when the frame never left. `SettleDeployment` is the only outcome writer, scoped to the endpoint that ran it: an `applying` row always settles; an `unknown` row only while its instance exists and no newer row for it is `applying` or settled, else `ErrNotFound`; a newer `planned` row does not block it and is expired in the same transaction. `RefuseDeploymentResult` selects rows by the same rule, scoped to its endpoint, and moves an `applying` row, or an `unknown` one with a different detail, to `unknown` with the caller's fixed detail and an `agent:<endpoint>` audit row (`outcome=refused`, `application.destroy` for a `remove` row); a repeat changes nothing and writes no audit row. Both take the application row lock (PostgreSQL) before the deployment row, the order Plan and Apply use. The row is locked (`FOR UPDATE` on PostgreSQL) and the final state write is conditional, so concurrent settles commit once. Each reported identity must name a distinct planned service at its pinned image ID (a pulled service instead needs `ImageDigest == pull_digest`; `res.Validate` already requires a full `ImageID`), and a success must report every planned service (`ErrInvalid` before any write). It rebinds each reported service's resource row to the new container, advances `current_revision`/`previous_revision` on success, stores the result code and steps (byte cap `MaxDeploymentResultStoredBytes`, checked in Go because the SQL CHECK counts characters) and writes an `agent:<endpoint>` audit row in the same transaction. `AbandonDeployments` marks an endpoint's `applying` rows `unknown` when its session ends; `Prune` does the same for rows two minutes past their deadline. These three transitions (`systemTransition`) select the rows, update each under the same filter and write one `system` audit row (`application.deploy`, `outcome=abandoned|swept|not_sent`, result `unknown`/`failure`) per row actually changed, in one transaction; a `remove` row audits as `application.destroy`.
- Migration 25 adds `deployments.kind` (`apply`/`remove`), allows `mapping_version` 0 only on a `remove` row (a never-mapped instance) and adds `applications.removed_at`. `RemoveApplication` (`application.destroy`, typed project confirm, audit target `<app>/deployments/<id>`) locks the application row, requires the instance, an active endpoint and no live row (`ErrDeploymentPlanned`/`ErrDeploymentInProgress`; expired plans are deleted), and inserts a `remove` row straight in `applying` at the latest revision whose plan lists every adopted resource (`containers`: service or `unmapped-<12 hex>`, ID, image ID, whole-second creation time, name) and returns the validated `protocol.RemovalRequest` (at most `protocol.MaxRemovalTargets`, 100; more is `ErrRemovalTooLarge`). Before inserting it reads the endpoint inventory through `freshInventory` (stale or partial is `ErrAdoptionChanged`) and refuses with `PreflightBlockedError` naming `unadopted_project_containers` (a container of the project that is not an adopted resource) and/or `apply_outcome_unknown` (the instance's newest non-planned row is an `unknown` apply). Its success audit row carries details `project=<p> endpoint=<id> containers=<n>` through `withTenantTargetDetails`. `SettleDeployment` on a `remove` row refuses identities and steps outside the plan's targets or kinds (`ErrInvalid`), forgets each target whose precondition succeeded and then whose `remove` step succeeded or whose stop and remove were skipped (already gone), and only on `succeeded` (which must account for every target) deletes the instance and sets `removed_at`; revisions and history stay, audit action `application.destroy`. `ListApplications` returns `removed_at`; `DiscardApplication` works on a removed application. `Prune` deletes settled rows past `DeploymentHistoryRetention` (90 days) except the latest succeeded apply row at each of their instance's current and previous revisions and any row of a removed application, and applications removed longer than `ApplicationRemovedRetention` (90 days; `AdoptApplication` clears `removed_at`, and one with an instance is skipped) with their deployments and revisions.
- Migration 29 adds `deployments.correlation_id` (`TEXT NOT NULL DEFAULT ''`). `PlanDeployment` and `RemoveApplication` store the request's `CorrelationID` (the API's `X-Request-ID`; minted as a UUID when empty, before the transaction, so the plan's audit row and the row agree) and send it as the frame's `request_id`; `buildDeploymentFrame` refuses a row without one (`ErrAdoptionChanged`: planned before the upgrade, plan again). `ApplyDeployment` reads the row's correlation ID (scoped to organization, environment and application) and audits under it, so the apply request's own `X-Request-ID` names no row; `auditDeployment` takes the correlation ID, and `SettleDeployment`, `RefuseDeploymentResult` and every `systemTransition` (abandon, sweep, not sent) pass the row's (a fresh UUID for a row planned before migration 29). `Deployment.CorrelationID` (`correlation_id`) is on every deployment read. `SettleDeployment` first reads the result through `legacyResult` (only a result with no `request_id`, from a binary built before codes: each missing step or result code becomes `legacy`, its text dropped), refuses one that still fails `Validate` with `ErrUnreadableResult` (nothing written), and refuses a non-empty `request_id` other than the row's with `ErrInvalid`. The result column holds `{code, steps, services}` (codes and parameters only) and settling clears the row's `detail`; `scanDeployment` reads a result stored before outcome codes through `legacyResult`.
- Migration 22 adds per-instance mapping_version/mapped_revision and per-resource service_name, unique for nonempty names within an instance. Mapping assigns each current definition service to at most one already adopted immutable ID (or leaves it unmapped). Read under application.read; write under application.adopt, rechecking instance, mapping version, typed project and complete adoption digest under application/endpoint locks plus instance CAS. All adopted identities must remain in the current project with the same image and creation time (microsecond precision). No labels grant assignments, no runtime changes. Definition revisions make mappings stale; release deletes them. A mapping write refuses with `ErrDeploymentInProgress` while a deployment for the instance is `applying`, because settling rebinds its resources. SQLite recovery covers the columns.
- `ReplaceApplicationRevision` (`application.edit`) saves a complete parsed definition and encrypted value bundle at expected head + 1 in the same authorization/audit transaction. Bind encryption to that exact revision, scope and spec digest; never copy old values implicitly. Invalid values/key, stale head, history quota or audit failure roll back head/history/bundle together. Imported revision 1 and later bundles survive SQLite recovery. The internal spec-only `AppendApplicationRevision` does not create a secret bundle and is not the public edit path.
- `CompareApplication` uses `application.read` and explicit environment scope to compare the latest digest-verified revision with adopted immutable identities and the current stored inventory. It returns no observations for unavailable, stale, corrupt or container-truncated inventory. At most 2,000 rows (1,000 owned plus 1,000 observed) are advisory only; service labels/image-reference equality never establish deployment authority or configuration parity. No secret resolution, new persistence or runtime dispatch.
- Migration 21 adds one `application_instances` placement per application and `application_resources` with unique endpoint/container ownership. Composite FKs bind application, revision and endpoint to one environment and restrict draft deletion. Adoption requires `application.adopt`, active Docker, a complete container snapshot received within three minutes and observed within five, and a digest over application/head/host/project and sorted immutable IDs/names/image IDs/creation times, with each container's reported mounts (`AdoptedContainer.Mounts`, nil when unreported, and `MountsTruncated`; not stored in `application_resources`). Lock application then endpoint while rechecking and committing instance/resources/audit. One endpoint holds at most 1,000 adopted container records. Labels select candidates only; they never grant ownership or reconstruct desired config. Networks/volumes are unowned. `ReadApplicationInstance` (`application.read`) reads one instance scoped to organization, environment and application, without its containers.
- `application.release` conditionally deletes exactly the confirmed instance/project and its ownership rows, with audit; it never dispatches commands. Adopted applications cannot be discarded until released. Environment lists return ownership counts only; endpoint lists include at most 1,000 resource records. Snapshot backup coverage includes both tables and resource identities. Release refuses while an unexpired deployment plan exists for the instance.

- Migration 20 stores an encrypted environment bundle alongside imported revision 1. Import validates an exact reference/value match and seals at most 64 KiB of JSON, with 16 KiB per value, under an encryption-key-derived key bound to organization/environment/application/revision/spec digest. `ResolveApplicationSecrets` is internal-only, requires `secret.reveal`, verifies digest/ciphertext/reference consistency and commits audit before returning values. Both it and `ApplyDeployment` decrypt through `resolveApplicationValues`, which owns no permission or audit of its own. Ordinary reads omit ciphertext and values. Snapshot restoration is tested using the encryption key recovered from the payload.
- Tenant transaction audits and `Audit.LogAudit` sanitize/bound resource text to 255 UTF-8 bytes before inserts. Migration 19 enforces the same bound on new database inserts on both backends while preserving historical rows. Malformed application IDs are input errors before the authorization/audit operation; valid denied operations still audit.
- Migration 18 adds `applications` and immutable `application_revisions`, with same-organization/environment foreign keys and environment-local application name uniqueness. `CreateApplication` (`application.import`) commits revision 1 and audit together; `AppendApplicationRevision` (`application.edit`) conditionally advances the expected head and inserts history in the same transaction, returning `ErrRevisionConflict` for a stale edit. Application IDs are parsed before forming audit targets; revision reads recompute the stored-byte digest and refuse mismatches with `ErrRevisionCorrupt`. Reads require `application.read` and explicit environment scope. Environment removal refuses remaining applications. Creation locks the organization row for a 100-application quota; each application has at most 100 revisions of 64 KiB, pruned only with a removed application. Explicit `DiscardApplication` (`application.destroy`) deletes an undeployed draft and its history only at the expected head, atomically with audit; this releases quota and permits environment deletion. Instance references restrict draft deletion. The typed spec supports service names/images, restart, long-form published ports, environment secret references and volumes, never raw Compose or arbitrary JSON. Volume bounds (`encodeApplicationSpec`): at most 64 `DeclaredVolume`s per spec with unique names matching `[a-zA-Z0-9][a-zA-Z0-9_.-]{0,63}` (`ValidVolumeName`), at most 32 `ApplicationVolume`s per service; kind is `named` (source a declared name) or `bind` (source passes `CleanAbsolutePath`: absolute, `path.Clean`ed, no surrounding whitespace, display-safe and so at most 255 bytes); target passes `CleanAbsolutePath`, is not `/` and is unique per service. `ValidVolumeName` stays `{0,63}` because `ValidateApplicationSpec` also runs on stored revisions at preflight, mapping and comparison, and a revision saved before the two-character minimum must keep validating. `ValidDeclaredVolumeName` (`{1,63}`, at least two characters) is the grammar for a newly declared name; the importer (`internal/applications/compose.go`) uses it, not `ValidVolumeName`, so a one-character name can no longer be declared. Both and `CleanAbsolutePath` are exported so the importer refuses at a position; these store checks remain the backstop. `Volumes` fields are last and `omitempty`, so a volume-free spec encodes and digests exactly as before. `VolumeHostName` gives the runtime name: `Name` when external, else `<project>_<Name>` as Compose does. Public import/list/read/edit/discard routes exist. `TestApplicationRevisionsSurviveBackup` proves both tables and revision digests survive the collected SQLite snapshot.
- `CheckExecAccess` authorizes socket admission through the tenant read path. `OpenExecTarget` requires `container.exec`, active endpoint scope, full immutable IDs, an explicit container user and a running inventory target whose name/image match confirmation. Live authorization, permission audit and the scoped `container.exec.open` intent commit together before dispatch. The open result is unknown until the API records a close with inspected exit status; an unmatched open after a crash stays unknown. Audit stores user, stream, image and target metadata, never argv or terminal contents. Exec rechecks through `StillAllowed` also require an active endpoint, so revocation outside the HTTP handler closes existing terminals. Existing SQLite snapshots and audit retention cover these rows.
- `InitializeLocalDocker` is trusted startup-only bootstrap: atomically create an approved `ep_local_docker` in the initial organization’s Local environment, its public key and audit record. The `local_docker_initialized` settings marker serializes initialization and survives endpoint/environment deletion; restarts never replace keys, restore revoked authority or regrant membership. Return the last stored inventory generation for reconnect. Existing SQLite snapshots cover these rows without new tables.
- Migration 5 creates organizations, fixed-role/status memberships, environments and organization-local groups. Legacy SCIM groups remain global identity data and confer no tenant membership. Composite group/member foreign keys enforce same-organization references; deleting a membership cascades its group links, so rejoining does not restore them.
- Tenant roles are `organization_admin`, `environment_admin`, `operator`, `developer`, `read_only`. Global `User.Role=admin` remains platform authority and is not a tenant role. Raw persistence methods are trusted bootstrap/management helpers. HTTP routes use the authorized `ReadOrganization`, `ReadEnvironment`, `ListEnvironments`, `AddEnvironment`, `UpdateEnvironment`, `RemoveEnvironment`, `ReadAudit`, `ListMembers`, `PutMembership` and `RemoveMembership` methods. `ListMemberOrganizations` is the one identity-scoped read: it takes the authenticated user's ID and returns only that user's active memberships.
- `CreateOrganizationWithAdmin` and `ListOrganizations` are trusted platform-administration methods (the API enforces platform `admin`). Creation inserts the caller-supplied organization and its first `organization_admin`/`active` membership in one transaction: the admin's `status` is read `FOR UPDATE` on PostgreSQL (so a concurrent status change waits behind the membership insert or is seen by it; `TestCreateOrganizationWithAdminLocksTheUser` holds the row, flips the status and asserts `ErrInvalid`); missing user `ErrNotFound`, user not `active` `ErrInvalid`, exact (case-sensitive) name taken `ErrAlreadyExists`. Migration 28 adds the unique index `idx_organizations_name`; the insert uses `ON CONFLICT (name) DO NOTHING` and zero rows affected is `ErrAlreadyExists`, so concurrent same-name creates yield exactly one organization with no lock. `ListOrganizations` orders by name then ID and counts only active memberships.
- Migration 30 creates `idx_users_username_lower` (`UNIQUE (LOWER(username))`, one statement for both dialects), which `GetUserByUsername`'s `LOWER(username)=LOWER(?)` sign-in lookup relies on. Its `Check` (`migrations.Migration.Check`, run in the migration's transaction before the SQL) refuses a database holding usernames that differ only by case with `usernames differ only by case: "<name>", "<name>"; "<group>"; rename or delete one of each pair before upgrading` (each name quoted with `%q` so a provider-supplied name with control characters cannot corrupt the log line, in creation order joined by `, ` within a group, groups by lowercase name), altering nothing, so the server does not start until an operator resolves them (README.md, `## Upgrading`). `CreateUser` and `UpdateUser` map a violation of either unique index to `ErrAlreadyExists`, never the driver's text.
- Every environment/group operation requires its organization ID; names are unique within that organization. `GetMembership` returns status for management; permission checks must additionally require both an active membership and an active user. No global-user/SCIM role implies tenant access.
- `Tenancy.Initialize` runs after account bootstrap, once per database: it grants initial organization administration to the active local admin named `admin`, otherwise the oldest active local admin (creation time then ID). With users but no eligible local admin, it completes without a grant; future administration must explicitly add membership. With zero users it fails and rolls back. Other organizations never receive implicit memberships.
- Bootstrap claims its singleton marker, inserts the membership and records `organization.bootstrap` in one transaction. Concurrent calls serialize on the marker; failed calls retry. Restarts and account resets never regrant removed or disabled memberships. SQLite capsule snapshots include the tenant tables and marker automatically.
- `CompletePasswordChange` atomically compares the old password, updates a flagged local account, clears the flag, deletes sessions/MFA challenges/device pairings and records `auth.password_changed`. Session/MFA issuance locks the same user row against the verified hash; MFA challenges persist the creation-time password hash, and consumption returns that snapshot to reject stale completions. Migration 4 discards preexisting challenges because their credential snapshot is unknown.
- `ResetAdminPassword` reactivates a local administrator with the replacement flag set and shares the atomic grant purge and audit path with `CompletePasswordChange`; it also works for disabled accounts.
- `store.Open(ctx, cfg)` initializes and auto-migrates the configured database backend.
- SQLite defaults to WAL mode. Every connection DSN independently enables foreign keys even when custom tuning pragmas are supplied; open verifies `PRAGMA foreign_keys=1` and fails closed on conflicting options. Tenant reference/cascade guarantees depend on this check.
- PostgreSQL queries are rebound dynamically from standard positional parameters.
- MFA challenges and device pairings are consumed with database state transitions that permit exactly one successful use.
- Recovery-code hash updates use optimistic concurrency so simultaneous redemption cannot reuse a code.

- `withTenant` (mutations) locks the acting membership before checking live user status, password-replacement state, membership status and the named action from `internal/permissions`; PostgreSQL uses `FOR UPDATE` on the user/membership join, SQLite takes its single writer lock with a no-op membership write so a concurrent revocation waits instead of racing. `readTenant` (reads) performs the same checks on a plain snapshot with no lock and no write. Keep authorization, scoped SQL and successful audit in one transaction. Revocation cannot overtake an authorized mutation. Sessions are authenticated per request against the live user row and password replacement revokes them, so there is no separate credential snapshot.
- A caller with no membership in the named organization gets `ErrForbidden` and no audit row: the URL scope is unverified, and a tenant row there would let any account write into another organization's history without bound. Members' denials and failures are recorded in their organization.
- Migration 6 labels historical audit rows `platform`/`unknown` without inventing tenant attribution. New tenant events carry organization/environment, actor (`user_id`), target (`resource`), correlation, action, result and time; audit scope IDs deliberately have no foreign keys so deletion preserves history. Failed operations roll back and log a separate failure/denial without SQL errors, names, bodies or credentials. Audit-write failure aborts successful operations.
- Migration 7 adds `endpoints` (unique name per organization, composite foreign key to its environment with `ON DELETE RESTRICT`), `endpoint_keys` (hex public key, state `pending_review`/`approved`/`retired`) and `agent_enrollment_tokens` (SHA-256 of a 32-byte token, 15-minute life, `consumed_at`). `CheckEnrollmentAccess` uses the shared authorized-read path (including environment scope and denial auditing) before Docker discovery; `CreateEnrollmentToken` independently rechecks live authorization with its atomic write/audit, needs an environment in scope, records the agent image reference the operator was handed (`agent_image`), and returns the raw secret once. `Enroll` is agent-facing: it verifies the proof of possession under the enrollment context (`internal/agent/protocol`), consumes the token with one conditional `UPDATE` so exactly one concurrent caller wins, creates the endpoint `pending` bound to the token's organization, environment and runtime, keeps only the known fact keys (4 KiB total, 255 bytes per value) and refuses, for names and fact values alike, control characters, Unicode line/paragraph separators and bidi controls (`displaySafe`, shared with environment names), so no agent-supplied text can forge or reorder a line in the approval dialog or a log, and audits `agent.enroll` as actor `agent:<endpoint>`; every refusal is `ErrForbidden`, a name clash `ErrAlreadyExists`. `ApproveEndpoint` requires the reviewed fingerprint to be the pending key and a pending age under 24 hours (older reads as `expired`); `RejectEndpoint` and `RevokeEndpoint` are the one terminal transition, retiring keys. `RemoveEnvironment` refuses with `ErrInUse` while a non-revoked endpoint remains, then deletes revoked history with the environment.
- Migration 17 adds `reference` to `endpoint_commands`: an image action stores its reference there and leaves `container_id` empty, because a row that kept an image reference in the container column would read as a container to everything downstream.
- Migration 16 adds `endpoint_commands`: durable intent, written before the frame goes out. `CreateCommand` authorizes the permission its action needs (`container.operate` for start, stop and restart; `container.destroy` for remove), requires a stated `expects.state` for destructive actions and a `confirm` matching the container's name as the last inventory recorded it (comparing the request against itself would attest to nothing, and an endpoint that has reported no inventory has nothing to confirm against). The command then travels as the container **ID** that confirmation resolved to, never the name: a name is a label the runtime reassigns, so a compose recreate between the inventory and the execution would otherwise confirm one container and destroy another; destructiveness follows the permission rather than a parallel list, so a future action given `container.destroy` inherits both requirements; accepts only Docker's own name/ID grammar for the container (`displaySafe` is the wrong gate for a value that becomes part of a URL: it permits a slash, a query and a fragment), binds organization, environment and endpoint, and refuses with `ErrEndpointOffline` unless the endpoint is active. `SettleCommand` writes an outcome only while one is absent, so the first answer wins; `AbandonCommands` settles everything dispatched and unanswered as `unknown` when a session ends. `Prune` ages out settled commands after `CommandRetention` (7 days) and never touches an unsettled one, because a command whose outcome nobody knows is the record an operator most needs.
- `ReconcileAfterStart` (trusted, startup only; `cmd/server` calls it after `Initialize`) settles every `endpoint_commands` row with `outcome=''` as `unknown` with detail `the server restarted before a result arrived`, in one transaction. `outcome=''` is the only condition (`dispatched_at`/`settled_at` are ignored): a never-dispatched row can never be sent after a restart, and the first real answer still wins.
