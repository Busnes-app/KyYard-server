# Storage Layer

## Purpose
Provides the unified Database Abstraction Layer (DAL) supporting pluggable backends (SQLite zero-CGO default and PostgreSQL enterprise) with automated dialect-aware migrations.

## Ownership
Owns data models, store interfaces (`UserStore`, `SessionStore`, `DeviceStore`, `GroupStore`, `AuditStore`, `SettingsStore`, `TenancyStore`), dialect translations, and schema migrations.

## Local Contracts
- `ReadInspectionTarget` uses endpoint.read and explicit scope to derive full container/image IDs and creation seconds from fresh complete Docker inventory. Require active endpoint, bounded valid snapshot and exactly one matching immutable ID. Re-read before publishing live inspection results; no successful-read audit, command or secret access.
- `PreflightApplication` is an application.read diagnostic over the latest digest-verified spec (the shared `preflight` takes a saved revision, 0 for latest; a missing one is `ErrNotFound`, and the head and mapping checks stay against the latest), confirmed mapping and fresh complete container inventory. Recheck instance/version/head and owned immutable identities across reads. Return endpoint ID and an optional validated inspection target derived only from the mapped owned container identity, independently of desired-image resolution. On the latest revision a binding to a service it does not define blocks as `unassigned_adopted_containers` and an unbound service as `service_unmapped`; a prior revision whose services are not exactly the mapped ones blocks once as `revision_services_differ`. `freshInventory` holds the inventory freshness rules (active endpoint, received within 3 minutes, observed within 5, complete and unique container list) shared with removal. A mapped service whose owned identity fails validation (not a full `sha256:` image ID with positive creation time) blocks as `replacement_identity_invalid`. Resolve exact local references only to full image IDs; incomplete/ambiguous image inventory cannot resolve. Report conservative published-port overlaps outside mapped replacements and within the definition. Each service's `mounts` is its volumes resolved (`resolveMounts`: `named` to kind `volume` with `VolumeHostName(preview project, declared)`, `bind` as written). On a mapped container whose mount list is missing (an agent older than mounts: every plan blocks until the agent is upgraded; the preview is rebuilt from live inventory, so the next report clears it) or truncated, the service blocks as `mounts_unreported`. Otherwise a definition bind with no identical container mount (kind, source, target and read-only by exact string, as reported: `/data/` is not `/data`, symlinks are not resolved) blocks as `bind_mount_new`; a container mount the agent refuses to replace (kind `other` such as tmpfs, or an anonymous volume, a 64-hex name) blocks as `mount_unsupported` and is listed in `unsupported_mounts`; any other container mount with no identical definition mount (read-only included, so a ro to rw change shows the old mount dropped) is in `dropped_mounts`, binds also in `dropped_binds`, and does not block. A service naming an `external` volume absent from the inventory's volume list, or while that list is truncated, blocks as `volume_missing`; project volumes are never checked (the agent creates them). External names stay in the plan's `volumes`; the blocker is what stops the agent creating one. `executable` is true exactly when no blocker (top-level or per service) remains; never resolve secrets, persist pins or dispatch commands. See docs/application-schema.md for inventory limitations. `clock_skew` (top level) when the inventory row's `observed_at` (agent clock) and `received_at` (server clock) differ by more than `protocol.MaxClockSkew`; `freshInventory`'s windows are unchanged.
- `PlanDeployment` (`application.deploy`) plans any saved revision (`PlanRequest.Revision`, 0 for latest) and mints a persisted plan only from a clean preflight (any blocker refuses with `PreflightBlockedError`); a mismatched instance/mapping version/revision/typed project is `ErrAdoptionChanged`. Migration 23's `deployments` table holds the plan; migration 24's `idx_deployments_live` allows one `planned` or `applying` row per instance, and a re-plan replaces a `planned` one inside the same locked transaction (refusing with `ErrDeploymentInProgress` while one is `applying`), with the JSON plan (pinned image IDs, single-match repository digests, replaced-container identity, restart, ports, sorted secret ref names, the preflight's resolved `mounts` per service, its `dropped_mounts` when non-empty (shown on the plan for approval), and `volumes`, the distinct volume host names in first-use order) capped at `MaxDeploymentPlanBytes`. `PlanDeployment(ctx, a, app, r, resolver, key, privateAllowed)`: every plan needs a 32-byte key (`ErrInvalid` otherwise); a plan without `r.Update` is that single locked transaction and needs no resolver. With `Update` (more than `protocol.MaxDeploymentServices` names, duplicates or a nil resolver are `ErrInvalid` before any audit) it runs the `CheckImageUpdates` phases under target `<app>/deployments/<id>`: read (`run`, no lock, no success row) drafts the plan (`draftPlan`), blocks `update_not_mapped` for a name that is not a service of the planned revision with a binding, `registry_not_configured` for a host with no row while anonymous pull is off, `registry_unavailable` for an unparsable reference, pins a digest reference directly with no registry call (it still needs a configured host or anonymous pull), and records `imageCheckStateOf`; resolve (`resolveImageChecks`, no transaction) maps errors to `registry_<detail>` blockers and a non-sha256 answer to `registry_unavailable`; write (`withTenantTargetDetails` on `context.WithoutCancel`) takes `lockApplication`, refuses a changed state with `ErrAdoptionChanged`, then refuses blockers or inserts (`insertPlan`) with details `pulls=N`. A pulled service records `pull_reference` (`registry.ParseReference` host + `/` + repository + `@` + digest, so `protocol.ImagePull.Host()` equals the registry row's host) and `pull_digest`; `image_id` stays the running image. `ApplyDeployment` sends it as `ImagePull{Reference, Digest, Tag}`, `Tag` being the spec reference in canonical form (`ParseReference` host + `/` + repository + `:` + tag; empty for a digest-pinned reference), and refuses (`ErrInvalid`, row stays `planned`) a frame larger than the `maxFrameBytes` the API passes for the endpoint (`protocol.MaxDeploymentRequestBytesLegacy` without `deployment.pull`). Once no other blocker remains, `checkFrame` builds the frame apply would send (`buildDeploymentFrame`, shared with apply: values and credentials decrypted in memory), measures it with `frameBlocker` against `PlanRequest.MaxFrameBytes` (set by the API from the endpoint's capabilities, `json:"-"`) and drops it: `too_many_registry_hosts` over 16 credentialed hosts, `frame_invalid` for any other `Validate` failure, `frame_too_large` past `min(MaxFrameBytes, 320 KiB)`. Nothing from the frame is stored. `ReadDeployment`/`ListDeployments` (`application.read`) carry `kind` and the endpoint's current name (joined at read, empty once the endpoint is gone) and compute `expired` from `DeploymentPlanTTL` (10 minutes) without rewriting state. `ReleaseApplication` locks the application row (same lock and order preflight uses for a plan) before checking; it deletes expired plan rows and refuses with `ErrDeploymentPlanned` while an unexpired one exists, and its live check and DELETE are scoped to organization, environment, application and instance under that lock, so a concurrent plan's uncommitted insert cannot be invisible to release on PostgreSQL. See docs/application-schema.md, Deployment plans. `draftPlan` reads `endpoint_capabilities` (`endpointCapabilities`) and `capabilityBlockers` adds `agent_deploy_unsupported` without `deployment.apply`, `agent_inspect_unsupported` without `container.inspect` or `container.inspect.verdict` (`inspectsVerdicts`), and, once pulls are pinned (the update path checks again after resolving), `agent_pull_unsupported` for a pulling plan without `deployment.pull`. Apply keeps its own 501s: capabilities can change between plan and apply. With both, every mapped service (one with an `InspectionTarget`) needs `PlanRequest.Inspections[containerID]` (`json:"-"`, set by the API): none is `inspection_unavailable`, a `Target` other than the preflight's is `replacement_identity_changed`, `ConfigurationVerified` false is `configuration_unsupported` with the codes on `PreflightService.Unsupported`. `PreflightBlockedError.Services` lists each service with blockers of its own as `BlockedService{name, blockers, unsupported}`. The inspections are consumed and never stored.
- `ApplyDeployment` (`application.deploy`, typed project confirm) locks the application row, then rechecks that the plan is `planned` (`ErrDeploymentInProgress` if already `applying`; a wrong confirm is `ErrInvalid`), unexpired, of kind `apply`, at a revision between 1 and the head with its stored spec digest, the instance's mapping version, an active endpoint and each replaced container's resource row; it builds the frame with `buildDeploymentFrame` (`IssuedAt` now; a service with `pull_digest` goes as `Pull` with an empty `ImageID`, and `Registries` holds `registryFor`'s credential, under the same key, once per pulled host that has one; a pulled host with no row while anonymous pull is off is `ErrAdoptionChanged`, row still planned) and refuses any `frameBlocker` finding with `ErrInvalid` before moving the row to `applying` by compare-and-set. The frame's per-service `Mounts` and its `Volumes` are the plan's, unchanged; spec and plan caps keep them far below the frame bound, which stays the guard. Values and registry credentials exist only in the returned request, never in a row or audit. `FailDeployment` marks an `applying` or `unknown` row failed when the frame never left. `SettleDeployment` is the only outcome writer, scoped to the endpoint that ran it: an `applying` row always settles; an `unknown` row only while its instance exists and no newer row for it is `applying` or settled, else `ErrNotFound`; a newer `planned` row does not block it and is expired in the same transaction. `RefuseDeploymentResult` selects rows by the same rule, scoped to its endpoint, and moves an `applying` row, or an `unknown` one with a different detail, to `unknown` with the caller's fixed detail and an `agent:<endpoint>` audit row (`outcome=refused`, `application.destroy` for a `remove` row); a repeat changes nothing and writes no audit row. Both take the application row lock (PostgreSQL) before the deployment row, the order Plan and Apply use. The row is locked (`FOR UPDATE` on PostgreSQL) and the final state write is conditional, so concurrent settles commit once. Each reported identity must name a distinct planned service at its pinned image ID (a pulled service instead needs `ImageDigest == pull_digest`; `res.Validate` already requires a full `ImageID`), and a success must report every planned service (`ErrInvalid` before any write). It rebinds each reported service's resource row to the new container, advances `current_revision`/`previous_revision` on success, stores the steps (byte cap `MaxDeploymentResultStoredBytes`, checked in Go because the SQL CHECK counts characters) and writes an `agent:<endpoint>` audit row in the same transaction. `AbandonDeployments` marks an endpoint's `applying` rows `unknown` when its session ends; `Prune` does the same for rows two minutes past their deadline. These three transitions (`systemTransition`) select the rows, update each under the same filter and write one `system` audit row (`application.deploy`, `outcome=abandoned|swept|not_sent`, result `unknown`/`failure`) per row actually changed, in one transaction; a `remove` row audits as `application.destroy`.
- Migration 25 adds `deployments.kind` (`apply`/`remove`), allows `mapping_version` 0 only on a `remove` row (a never-mapped instance) and adds `applications.removed_at`. `RemoveApplication` (`application.destroy`, typed project confirm, audit target `<app>/deployments/<id>`) locks the application row, requires the instance, an active endpoint and no live row (`ErrDeploymentPlanned`/`ErrDeploymentInProgress`; expired plans are deleted), and inserts a `remove` row straight in `applying` at the latest revision whose plan lists every adopted resource (`containers`: service or `unmapped-<12 hex>`, ID, image ID, whole-second creation time, name) and returns the validated `protocol.RemovalRequest` (at most `protocol.MaxRemovalTargets`, 100; more is `ErrRemovalTooLarge`). Before inserting it reads the endpoint inventory through `freshInventory` (stale or partial is `ErrAdoptionChanged`) and refuses with `PreflightBlockedError` naming `unadopted_project_containers` (a container of the project that is not an adopted resource) and/or `apply_outcome_unknown` (the instance's newest non-planned row is an `unknown` apply). Its success audit row carries details `project=<p> endpoint=<id> containers=<n>` through `withTenantTargetDetails`. `SettleDeployment` on a `remove` row refuses identities and steps outside the plan's targets or kinds (`ErrInvalid`), forgets each target whose precondition succeeded and then whose `remove` step succeeded or whose stop and remove were skipped (already gone), and only on `succeeded` (which must account for every target) deletes the instance and sets `removed_at`; revisions and history stay, audit action `application.destroy`. `ListApplications` returns `removed_at`; `DiscardApplication` works on a removed application. `Prune` deletes settled rows past `DeploymentHistoryRetention` (90 days) except the latest succeeded apply row at each of their instance's current and previous revisions and any row of a removed application, and applications removed longer than `ApplicationRemovedRetention` (90 days; `AdoptApplication` clears `removed_at`, and one with an instance is skipped) with their deployments and revisions.
- Migration 22 adds per-instance mapping_version/mapped_revision and per-resource service_name, unique for nonempty names within an instance. Mapping assigns each current definition service to at most one already adopted immutable ID (or leaves it unmapped). Read under application.read; write under application.adopt, rechecking instance, mapping version, typed project and complete adoption digest under application/endpoint locks plus instance CAS. All adopted identities must remain in the current project with the same image and creation time (microsecond precision). No labels grant assignments, no runtime changes. Definition revisions make mappings stale; release deletes them. A mapping write refuses with `ErrDeploymentInProgress` while a deployment for the instance is `applying`, because settling rebinds its resources. SQLite recovery covers the columns.
- `ReplaceApplicationRevision` (`application.edit`) saves a complete parsed definition and encrypted value bundle at expected head + 1 in the same authorization/audit transaction. Bind encryption to that exact revision, scope and spec digest; never copy old values implicitly. Invalid values/key, stale head, history quota or audit failure roll back head/history/bundle together. Imported revision 1 and later bundles survive SQLite recovery. The internal spec-only `AppendApplicationRevision` does not create a secret bundle and is not the public edit path.
- `CompareApplication` uses `application.read` and explicit environment scope to compare the latest digest-verified revision with adopted immutable identities and the current stored inventory. It returns no observations for unavailable, stale, corrupt or container-truncated inventory. At most 2,000 rows (1,000 owned plus 1,000 observed) are advisory only; service labels/image-reference equality never establish deployment authority or configuration parity. No secret resolution, new persistence or runtime dispatch.
- Migration 21 adds one `application_instances` placement per application and `application_resources` with unique endpoint/container ownership. Composite FKs bind application, revision and endpoint to one environment and restrict draft deletion. Adoption requires `application.adopt`, active Docker, a complete container snapshot received within three minutes and observed within five, and a digest over application/head/host/project and sorted immutable IDs/names/image IDs/creation times, with each container's reported mounts (`AdoptedContainer.Mounts`, nil when unreported, and `MountsTruncated`; not stored in `application_resources`). Lock application then endpoint while rechecking and committing instance/resources/audit. One endpoint holds at most 1,000 adopted container records. Labels select candidates only; they never grant ownership or reconstruct desired config. Networks/volumes are unowned. `ReadApplicationInstance` (`application.read`) reads one instance scoped to organization, environment and application, without its containers.
- `application.release` conditionally deletes exactly the confirmed instance/project and its ownership rows, with audit; it never dispatches commands. Adopted applications cannot be discarded until released. Environment lists return ownership counts only; endpoint lists include at most 1,000 resource records. Snapshot backup coverage includes both tables and resource identities. Release refuses while an unexpired deployment plan exists for the instance.

- Migration 20 stores an encrypted environment bundle alongside imported revision 1. Import validates an exact reference/value match and seals at most 64 KiB of JSON, with 16 KiB per value, under an encryption-key-derived key bound to organization/environment/application/revision/spec digest. `ResolveApplicationSecrets` is internal-only, requires `secret.reveal`, verifies digest/ciphertext/reference consistency and commits audit before returning values. Both it and `ApplyDeployment` decrypt through `resolveApplicationValues`, which owns no permission or audit of its own. Ordinary reads omit ciphertext and values. Snapshot restoration is tested using the encryption key recovered from the payload.
- Tenant transaction audits and `Audit.LogAudit` sanitize/bound resource text to 255 UTF-8 bytes before inserts. Migration 19 enforces the same bound on new database inserts on both backends while preserving historical rows. Malformed application IDs are input errors before the authorization/audit operation; valid denied operations still audit.
- Migration 18 adds `applications` and immutable `application_revisions`, with same-organization/environment foreign keys and environment-local application name uniqueness. `CreateApplication` (`application.import`) commits revision 1 and audit together; `AppendApplicationRevision` (`application.edit`) conditionally advances the expected head and inserts history in the same transaction, returning `ErrRevisionConflict` for a stale edit. Application IDs are parsed before forming audit targets; revision reads recompute the stored-byte digest and refuse mismatches with `ErrRevisionCorrupt`. Reads require `application.read` and explicit environment scope. Environment removal refuses remaining applications. Creation locks the organization row for a 100-application quota; each application has at most 100 revisions of 64 KiB, pruned only with a removed application. Explicit `DiscardApplication` (`application.destroy`) deletes an undeployed draft and its history only at the expected head, atomically with audit; this releases quota and permits environment deletion. Instance references restrict draft deletion. The typed spec supports service names/images, restart, long-form published ports, environment secret references and volumes, never raw Compose or arbitrary JSON. Volume bounds (`encodeApplicationSpec`): at most 64 `DeclaredVolume`s per spec with unique names matching `[a-zA-Z0-9][a-zA-Z0-9_.-]{0,63}`, at most 32 `ApplicationVolume`s per service; kind is `named` (source a declared name) or `bind` (source passes `CleanAbsolutePath`: absolute, `path.Clean`ed, no surrounding whitespace, display-safe and so at most 255 bytes); target passes `CleanAbsolutePath`, is not `/` and is unique per service. `ValidVolumeName` and `CleanAbsolutePath` are exported so the importer refuses at a position; these store checks remain the backstop. `Volumes` fields are last and `omitempty`, so a volume-free spec encodes and digests exactly as before. `VolumeHostName` gives the runtime name: `Name` when external, else `<project>_<Name>` as Compose does. Public import/list/read/edit/discard routes exist. `TestApplicationRevisionsSurviveBackup` proves both tables and revision digests survive the collected SQLite snapshot.
- `CheckExecAccess` authorizes socket admission through the tenant read path. `OpenExecTarget` requires `container.exec`, active endpoint scope, full immutable IDs, an explicit container user and a running inventory target whose name/image match confirmation. Live authorization, permission audit and the scoped `container.exec.open` intent commit together before dispatch. The open result is unknown until the API records a close with inspected exit status; an unmatched open after a crash stays unknown. Audit stores user, stream, image and target metadata, never argv or terminal contents. Exec rechecks through `StillAllowed` also require an active endpoint, so revocation outside the HTTP handler closes existing terminals. Existing SQLite snapshots and audit retention cover these rows.
- `InitializeLocalDocker` is trusted startup-only bootstrap: atomically create an approved `ep_local_docker` in the initial organization’s Local environment, its public key and audit record. The `local_docker_initialized` settings marker serializes initialization and survives endpoint/environment deletion; restarts never replace keys, restore revoked authority or regrant membership. Return the last stored inventory generation for reconnect. Existing SQLite snapshots cover these rows without new tables.
- Migration 5 creates organizations, fixed-role/status memberships, environments and organization-local groups. Legacy SCIM groups remain global identity data and confer no tenant membership. Composite group/member foreign keys enforce same-organization references; deleting a membership cascades its group links, so rejoining does not restore them.
- Tenant roles are `organization_admin`, `environment_admin`, `operator`, `developer`, `read_only`. Global `User.Role=admin` remains platform authority and is not a tenant role. Raw persistence methods are trusted bootstrap/management helpers. HTTP routes use the authorized `ReadOrganization`, `ReadEnvironment`, `ListEnvironments`, `AddEnvironment`, `UpdateEnvironment`, `RemoveEnvironment`, `ReadAudit`, `ListMembers`, `PutMembership` and `RemoveMembership` methods. `ListMemberOrganizations` is the one identity-scoped read: it takes the authenticated user's ID and returns only that user's active memberships.
- `CreateOrganizationWithAdmin` and `ListOrganizations` are trusted platform-administration methods (the API enforces platform `admin`). Creation inserts the caller-supplied organization and its first `organization_admin`/`active` membership in one transaction: missing user `ErrNotFound`, user not `active` `ErrInvalid`, exact (case-sensitive) name taken `ErrAlreadyExists`. Migration 28 adds the unique index `idx_organizations_name`; the insert uses `ON CONFLICT (name) DO NOTHING` and zero rows affected is `ErrAlreadyExists`, so concurrent same-name creates yield exactly one organization with no lock. `ListOrganizations` orders by name then ID and counts only active memberships.
- Every environment/group operation requires its organization ID; names are unique within that organization. `GetMembership` returns status for management; permission checks must additionally require both an active membership and an active user. No global-user/SCIM role implies tenant access.
- `Tenancy.Initialize` runs after account bootstrap, once per database: it grants initial organization administration to the active local admin named `admin`, otherwise the oldest active local admin (creation time then ID). With users but no eligible local admin, it completes without a grant; future administration must explicitly add membership. With zero users it fails and rolls back. Other organizations never receive implicit memberships.
- Bootstrap claims its singleton marker, inserts the membership and records `organization.bootstrap` in one transaction. Concurrent calls serialize on the marker; failed calls retry. Restarts and account resets never regrant removed or disabled memberships. SQLite capsule snapshots include the tenant tables and marker automatically.
- `CompletePasswordChange` atomically compares the old password, updates a flagged local account, clears the flag, deletes sessions/MFA challenges/device pairings and records `auth.password_changed`. Session/MFA issuance locks the same user row against the verified hash; MFA challenges persist the creation-time password hash, and consumption returns that snapshot to reject stale completions. Migration 4 discards preexisting challenges because their credential snapshot is unknown.
- `ResetAdminPassword` reactivates a local administrator with the replacement flag set and shares the atomic grant purge and audit path with `CompletePasswordChange`; it also works for disabled accounts.
- `store.Open(ctx, cfg)` initializes and auto-migrates the configured database backend.
- SQLite defaults to WAL mode. Every connection DSN independently enables foreign keys even when custom tuning pragmas are supplied; open verifies `PRAGMA foreign_keys=1` and fails closed on conflicting options. Tenant reference/cascade guarantees depend on this check.
- PostgreSQL queries are rebound dynamically from standard positional parameters.
- MFA challenges and device pairings are consumed with database state transitions that permit exactly one successful use.
- Recovery-code hash updates use optimistic concurrency so simultaneous redemption cannot reuse a code.

- `withTenant` (mutations) locks the acting membership before checking live user status, password-replacement state, membership status and the named action from `internal/permissions`; PostgreSQL uses `FOR UPDATE` on the user/membership join, SQLite takes its single writer lock with a no-op membership write so a concurrent revocation waits instead of racing. `readTenant` (reads) performs the same checks on a plain snapshot with no lock and no write. Keep authorization, scoped SQL and successful audit in one transaction. Revocation cannot overtake an authorized mutation. Sessions are authenticated per request against the live user row and password replacement revokes them, so there is no separate credential snapshot.
- A caller with no membership in the named organization gets `ErrForbidden` and no audit row: the URL scope is unverified, and a tenant row there would let any account write into another organization's history without bound. Members' denials and failures are recorded in their organization.
- Migration 6 labels historical audit rows `platform`/`unknown` without inventing tenant attribution. New tenant events carry organization/environment, actor (`user_id`), target (`resource`), correlation, action, result and time; audit scope IDs deliberately have no foreign keys so deletion preserves history. Failed operations roll back and log a separate failure/denial without SQL errors, names, bodies or credentials. Audit-write failure aborts successful operations.
- Migration 7 adds `endpoints` (unique name per organization, composite foreign key to its environment with `ON DELETE RESTRICT`), `endpoint_keys` (hex public key, state `pending_review`/`approved`/`retired`) and `agent_enrollment_tokens` (SHA-256 of a 32-byte token, 15-minute life, `consumed_at`). `CheckEnrollmentAccess` uses the shared authorized-read path (including environment scope and denial auditing) before Docker discovery; `CreateEnrollmentToken` independently rechecks live authorization with its atomic write/audit, needs an environment in scope, records the agent image reference the operator was handed (`agent_image`), and returns the raw secret once. `Enroll` is agent-facing: it verifies the proof of possession under the enrollment context (`internal/agent/protocol`), consumes the token with one conditional `UPDATE` so exactly one concurrent caller wins, creates the endpoint `pending` bound to the token's organization, environment and runtime, keeps only the known fact keys (4 KiB total, 255 bytes per value) and refuses, for names and fact values alike, control characters, Unicode line/paragraph separators and bidi controls (`displaySafe`, shared with environment names), so no agent-supplied text can forge or reorder a line in the approval dialog or a log, and audits `agent.enroll` as actor `agent:<endpoint>`; every refusal is `ErrForbidden`, a name clash `ErrAlreadyExists`. `ApproveEndpoint` requires the reviewed fingerprint to be the pending key and a pending age under 24 hours (older reads as `expired`); `RejectEndpoint` and `RevokeEndpoint` are the one terminal transition, retiring keys. `RemoveEnvironment` refuses with `ErrInUse` while a non-revoked endpoint remains, then deletes revoked history with the environment.
- Migration 17 adds `reference` to `endpoint_commands`: an image action stores its reference there and leaves `container_id` empty, because a row that kept an image reference in the container column would read as a container to everything downstream.
- Migration 16 adds `endpoint_commands`: durable intent, written before the frame goes out. `CreateCommand` authorizes the permission its action needs (`container.operate` for start, stop and restart; `container.destroy` for remove), requires a stated `expects.state` for destructive actions and a `confirm` matching the container's name as the last inventory recorded it (comparing the request against itself would attest to nothing, and an endpoint that has reported no inventory has nothing to confirm against). The command then travels as the container **ID** that confirmation resolved to, never the name: a name is a label the runtime reassigns, so a compose recreate between the inventory and the execution would otherwise confirm one container and destroy another; destructiveness follows the permission rather than a parallel list, so a future action given `container.destroy` inherits both requirements; accepts only Docker's own name/ID grammar for the container (`displaySafe` is the wrong gate for a value that becomes part of a URL: it permits a slash, a query and a fragment), binds organization, environment and endpoint, and refuses with `ErrEndpointOffline` unless the endpoint is active. `SettleCommand` writes an outcome only while one is absent, so the first answer wins; `AbandonCommands` settles everything dispatched and unanswered as `unknown` when a session ends. `Prune` ages out settled commands after `CommandRetention` (7 days) and never touches an unsettled one, because a command whose outcome nobody knows is the record an operator most needs.
- `ReconcileAfterStart` (trusted, startup only; `cmd/server` calls it after `Initialize`) settles every `endpoint_commands` row with `outcome=''` as `unknown` with detail `the server restarted before a result arrived`, in one transaction. `outcome=''` is the only condition (`dispatched_at`/`settled_at` are ignored): a never-dispatched row can never be sent after a restart, and the first real answer still wins. One audit row per endpoint: `user_id='system'`, action `endpoint.commands.reconciled`, resource the endpoint ID, details `commands=<n>`, scope `organization` with the commands' organization/environment, result `unknown`. Deployments are untouched (their sweep and agent ledger settle them). A second run changes nothing and audits nothing. Run exactly one server per database: every start settles all in-flight commands, including another live server's.
- Migration 9 adds `endpoint_events` (severity info/high, kind, details, acknowledged_at) and `endpoint_capabilities`. `RotateEndpointKey` verifies the current approved key's signature over the new key, refuses pending/revoked endpoints, refuses while an unacknowledged `duplicate_connection` event exists (`ErrRotationBlocked`) or a live pending key exists (`ErrRotationPending`), retires an expired pending key (7 days), inserts the new key as `pending_review`, records a high `rotation_pending` event naming both fingerprints, and audits `endpoint.rotate` with both. `AcknowledgeEndpointKey` (authorized, `endpoint.enroll`) approves exactly the named unexpired pending key, retires every other key and acknowledges the event. `AgentIdentity(endpoint, fingerprint)` returns `ErrKeyPendingReview` for a live pending key, `ErrKeyRetired` for retired or expired keys, and `ErrForbidden` for revoked/expired endpoints before looking at keys. `SetEndpointCapabilities` replaces the set (at most 64 display-safe strings, 4 KiB total; reads apply the same limit). `RecordEndpointEvent` refuses unsafe kind/details text and keeps one unacknowledged event per kind per endpoint (migration 11's partial unique index on `(endpoint_id, kind) WHERE acknowledged_at IS NULL`, inserts `ON CONFLICT DO NOTHING`, so parallel writers cannot slip past a prior read): a repeat while one stands is dropped, so a flood of one kind cannot grow the table or push other alerts out of the ten the endpoint view shows. The endpoint view's `pending_fingerprint` hides keys past the seven-day window.
- `AcceptInventory` refuses a generation more than an hour ahead of the server clock and records that refusal as a high-severity endpoint event so a bad clock cannot silently pin the inventory; approval and revocation reset `inventory_generation` and delete the stored snapshot, which is the operator's way out of a stuck endpoint.
- Successful reads write no audit row except the actions in `auditedReads` (`organization.audit.read`, `organization.members.manage`), which are low-volume and are what an incident review wants.
- `Usage`/`Budget`/`Pressure` are the disk budget (docs/retention-policy.md): `cmd/server`'s prune loop calls `EvaluatePressure` each pass with the rows that pass freed. The level rises to `PressureDegraded` at 95 % of `KY_RETENTION_DISK_BUDGET` and `PressureStopped` at 100 %, but only while usage is still growing, and any pass clears it. `Usage` is cheap rather than exact (SQLite pages minus the freelist; PostgreSQL's database size), and counts data `Prune` cannot reclaim, so a byte-only release would latch for the life of the server; the throttle that results is reported every fifteen minutes while the condition lasts. `Prune` shortens the raw sample window to one hour under either, because refusing writes alone never gives space back. Nothing in the audit path consults pressure.
- `RollUp(ctx, since)` summarises ended hours into `container_rollups` (migration 15) before the raw window drops them, covering only hours started at or after `since` so a pass costs one or two hours rather than the table; `cmd/server` passes the whole raw window on its first pass, then two hours, under a 30-second deadline because SQLite serves the process from one connection. A recompute may only widen an hour: pruning erodes the oldest in-window hour from below while the loop still runs over it, so the upsert lands only when it was computed from at least as many samples as the row it would replace. Without that, what survives the raw rows describes the hour's last minute. A reading the runtime would not answer for (-1) is counted in neither average nor peak, and an hour holding only those reports -1, so "no data" survives the summary. Summaries are pruned at `RollupRetention` (7 days), or `DegradedRollupRetention` (24 h) under disk-budget pressure so they give space back as the raw window does; the raw rows go at six hours, so a week of history costs 168 rows per container instead of 10,080. `ReadRollups` is an authorized read scoped like the raw one, capped at 200 rows.
- Migration 12 adds `container_samples`, migration 13 its `(endpoint_id, observed_at, container_id)` index and migration 14 `restart_count` (default -1, the runtime declining to answer, which rows written before it cannot tell from zero either); migration 11 (the open-event unique index) belongs to the rotation slice. It adds (primary key endpoint, container, observed_at). `RecordSamples` bounds the frame (1000 samples, display-safe container IDs), re-stamps skewed observations, drops samples inside a container's 50-second cadence (so about 360 rows per container per window whatever an agent sends), scopes cadence lookups to the frame's containers, probes the 100,000-row ceiling without scanning the whole table, and returns `ErrSampleBudget` when capacity is exhausted; the WebSocket reports `samples_budget_exhausted` and stays open, while malformed frames still return `ErrInvalid` and close the connection. `LatestSamples`/`ReadSamples` are authorized reads scoped like inventory; `Prune` deletes samples older than six hours and acknowledged events older than seven days in batches of 5,000 per store per pass, and `cmd/server` runs it every minute until a pass removes nothing (docs/retention-policy.md).
- Migration 10 adds `endpoint_inventory` (one row per endpoint: generation, observed_at, received_at, snapshot JSON). `AcceptInventory` checks the generation and stores the bounded snapshot (`MaxSnapshotBytes`, 1 MiB) in one transaction; `ReadInventory` is an authorized read scoped to organization and optional environment.
- Successful reads through `readTenant` no longer write an audit row (M4 decision in `docs/authorization-matrix.md`); denied and failed reads still do, and mutations are unchanged.
- Migration 8 adds `endpoints.inventory_generation`. The agent-session helpers are trusted and identity-keyed, never session-keyed: `AgentIdentity` returns the endpoint and the key its state allows (approved, or pending_review while pending); `AcceptInventory` applies only a higher generation and moves approved/offline to active; `TouchEndpoint` records heartbeats; `MarkEndpointOffline` only demotes active; `EndpointState` is the live check per frame; `RecordAgentConnect` audits with actor `agent:<endpoint>`.
- Membership management requires `organization.members.manage`. `PutMembership` upserts a fixed role/status for an existing user; `RemoveMembership` deletes. Both first lock the organization row (`FOR UPDATE` on PostgreSQL; SQLite already holds its single writer lock), so membership changes within one organization serialize, then count administrators whose membership and account are both active inside the same transaction and roll back with `ErrLastAdmin` at zero. This blocks the acting administrator from demoting, disabling or removing the last administrator, including concurrently with another; it does not cover platform-level account disablement, which `internal/store` users must handle separately. Membership audit rows carry the target user ID as `resource` (`withTenantTarget`); the organization stays in `organization_id`.
- Tenant audit reads filter organization (and optional validated environment), require organization administration and exclude platform history. Lists use bounded pagination (1–200, default 50 at HTTP).

- Migration 26 adds `registries` (one row per organization and normalised host, `UNIQUE(organization_id, host)`, cascade on organization delete) and `organizations.anonymous_pull_enabled` (default off). `NormalizeRegistryHost` lowercases, folds `index.docker.io`/`registry-1.docker.io` into `docker.io` (shared with `registry.CanonicalHost`) and, like `registry.ParseReference`, accepts only `localhost` or a name with a `.` or a port: DNS-style labels (no empty label, no label starting or ending in `-`), name at most 253 bytes, port 1..65535. Name 1..64 and username up to 255 must be unchanged by `protocol.CleanText`, and the username has no `:` (basic auth cannot carry it); the credential is at most 4 KiB of UTF-8 without NUL.
- The registry credential is write-only: sealed with AES-GCM under `DeriveKey(key, json(["kyyard/registry-credential/v1", org, id]))` so ciphertext cannot move between rows, and never returned by `ListRegistries`/`PutRegistry` (rows carry `has_credential`). `PutRegistry` (`registry.manage`) creates or updates by host under `lockOrganization`; `allow_private` without its `privateAllowed` argument (the operator's `KY_REGISTRY_ALLOW_PRIVATE`) is `ErrPrivateRegistriesDisabled` after the permission check (an audited failure, nothing written); `Credential` nil keeps, `""` clears. Audit target `registries/<id>` once the write succeeded (`registries` for a denial or failure before it) with details `host=<h> allow_private=<bool> credential=set|kept|cleared`; `DeleteRegistry` details `host=<h>`; `SetAnonymousPull` target `registry-policy`, details `old=<bool> new=<bool>`. Reads (`ListRegistries`, `ReadRegistryPolicy`) use `registry.read`.
- `ResolveRegistryAccess(ctx, a, action, ref, key, privateAllowed)` (internal only) runs under `action`, the permission of the operation that uses the credential (`application.deploy` or `image.pull`, an allow-list); any other action, including the read permissions every member holds, is `ErrForbidden` before the read. It parses the reference with `registry.ParseReference`, decrypts the host's credential inside the read transaction (`registryFor`), returns `Anonymous` for an unconfigured host only when the opt-in is on and `ErrRegistryNotConfigured` otherwise; a credential that does not decrypt is `ErrInvalid`, an audited failure of `action`; a role without `action` is an audited denial. It audits nothing else, including not configured, which it returns after the read so no row is written; callers audit the operation that uses it and never return the secret. The returned row's `AllowPrivate` is `stored && privateAllowed` (the operator's `KY_REGISTRY_ALLOW_PRIVATE`), re-checked on every use, so turning the opt-in off closes private egress for rows saved while it was on. The SQLite recovery drill proves the credential decrypts after restore with the recovered key.
- Migration 27 adds `image_checks` (primary key instance and service, cascade on instance delete): the cached update verdict per mapped service (`current`, `update_available`, `pinned`, `unknown_local`, `registry_error`; `detail` names the registry error) with local and remote digests. It holds no secret. `ReadImageChecks` (`application.read`, explicit environment) returns the instance, its mapping version and rows ordered by service; no instance is an empty result with `services: []`. Rows go with the instance (release, removal) and `settleApply` deletes them only on a succeeded apply, so a stale verdict never outlives the deployment that took it. The SQLite recovery drill proves a row survives restore.
- `CheckImageUpdateAccess(ctx, a, app)` is admission for the API's per-application check slot: `run` under `application.deploy` with target `<canonical app>/updates`, no lock and no success row (a member's denial is audited; a non-member's is not, as everywhere), `ErrInvalid` for a non-UUID or no environment, `ErrNotFound` when the application is not in the organization/environment. `CheckImageUpdates` re-authorizes; this only keeps unauthorized callers from seeing or holding the slot.
- `CheckImageUpdates(ctx, a, app, resolver, key, privateAllowed)` (`application.deploy`, explicit environment, 32-byte key, non-nil resolver) runs in three phases so no registry call holds a transaction. Read (`run` without lock or success row; denials and failures audit target `<app>/updates`): the mapping (`mapping_version < 1` is `ErrMappingRequired`, checked before `preflight`), then `preflight` on the latest revision (stale inventory or moved containers is `ErrAdoptionChanged`); one work item per service the latest revision defines and the mapping binds. It records the `imageCheckState` string (`mapping_version`, `latest_revision` and the instance's `(container_id, image_id)` pairs) built from the mapping and preflight it just checked, not a separate read. The local digest is the single entry of the bound container's image `Digests` whose `registry.ParseReference` host and repository equal the reference's and whose digest passes `validSHA256`; zero or several is `unknown_local`. A digest reference is `pinned`, an unparsable one `registry_error/unavailable`, a host with no registry row and anonymous pull off `registry_error/not_configured`: none of these calls the registry. Otherwise the credential comes from `registryFor` (nil when anonymous) and `allowPrivate` is the row's flag `&& privateAllowed`. Resolve (no transaction): `DigestResolver.Head`, at most `imageCheckConcurrency` (4) at once under `ImageCheckDeadline` (60s, exported so the API sizes its write deadline from it; a var tests shorten); the credential is dropped from the work item before the call. Equal digests are `current`, different `update_available`; errors map to `unauthorized`, `not_found`, `rate_limited`, `private_destination`, else `unavailable` (error text is never stored), and a service left at the deadline is `unavailable`. Write (`withTenantTargetDetails` on `context.WithoutCancel`, target `<app>/updates`): a request cancelled during the resolve phase returns the context error and audits a `failure` with the cached rows untouched; otherwise it first takes `lockApplication` (the `applications` row, `FOR UPDATE` on PostgreSQL; SQLite's writer lock already serializes), so a settle, remap or revision append cannot interleave with the comparison. A released instance or a changed `imageCheckState` (remap, new revision, settled apply) is `ErrAdoptionChanged` with nothing written; otherwise the instance's rows are replaced and the audit details are exactly `services=N updates=N errors=N`.
- `OpenLogTarget` authorizes `container.logs`, refuses an endpoint that is not connected, and resolves the identifier against the last inventory the way a destructive command does, answering with the container ID the stream must name. It is a read that writes an audit row (`auditedReads`): log bodies are never stored, so the record of who read one is the only trace there is.
- Migrations are append-only and numbered; `migrations.Latest()` returns the highest version, the schema this binary runs. `backup.Collect` pins it as the capsule recipe's `schema_version` and the drill compares it with `MAX(version)` in the restored `schema_migrations`, so every new migration changes what a capsule records. `migrations.Run` refuses a database whose `MAX(version)` exceeds `Latest()` (`database schema version N is newer than this binary (M)`): an older binary never serves a schema it has not read.
- `DigestResolver` is the store's one-method view of `registry.Client.Head`; an implementation must return once its context ends, because the check waits for every call.
- `run` takes the audit target by pointer and reads it at audit time, so an operation that learns its row inside the transaction (`PutRegistry`) names it; a denial before that audits the initial target.
