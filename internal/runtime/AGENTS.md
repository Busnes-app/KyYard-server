# Runtime adapters

## Purpose
Adapters that speak to a container runtime and return product types only. `docker` is the first; `kubernetes` follows in M8.

## Ownership
Owns the Engine API client (`docker.New` over the Unix socket, `docker.NewHTTP` for tests and TCP daemons), the mapping into `protocol.Snapshot`, and the bounds on what a snapshot may carry. SDK or wire types never leave this package; the protocol package owns the product types.

## Local Contracts
- `InspectContainer` is a GET adapter for a full container/image ID and whole-second creation identity. Read container, pinned image and container again under one 20-second deadline; reject changed selected facts. Project bounded operational fields and mount counts, including HostConfig.Tmpfs, with fixed errors and no raw config/paths/labels/argv/environment. Each body is capped at 1 MiB; mounts/networks/port bindings at 64. It reads the daemon's `DefaultRuntime` from `/info` first (cached per client for one minute; unreadable is `ErrInspectionUnavailable`), decodes the same container bodies into `inspectedForDeploy` and the `com.docker.compose.project` label, and reports `Unsupported`: `undescribed` with project network `<project>_default` (no label: `""`, so `network` unless on `bridge` only) plus `image_config` when the container's command, entrypoint, healthcheck, working directory or stop signal differ from the image's; `ConfigurationVerified` is true exactly when it is empty. A change in `Config`, `HostConfig` or `Mounts` between the two container reads is `ErrInspectionChanged`; both decodes sort `Mounts` (by destination, then source or type), because the Engine lists them from a map in no fixed order. Codes only: no value, path, label or name leaves. The path returns observations, never a recreation spec or deployment grant. See docs/application-schema.md, Runtime inspection foundation.
- `Client.Deploy` runs two phases. First, for every service in plan order: precondition, then a `volume` step for each `Volumes` name this service is the first to mount (below), then image present by pinned ID (`failed` when absent) or, for a service with `Pull`, the pull step below; any non-success there leaves every container untouched. Then, per service in plan order: recheck (a fresh `GET /containers/{id}/json`: `denied` `the container changed after the precondition` when `Id`, `Image` or `Created` second differ from `Replaces` or `Config`, `HostConfig` or `Mounts` differ by `reflect.DeepEqual` from the precondition's read kept on `prepared.before`, `Mounts` sorted on decode (`mountList`) so order is not drift; `State` and `NetworkSettings` are not compared; 404 is `denied` `the container no longer exists`), rename the running old container to `<name>.kyyard-prev-<deployment[:8]>`, create by image ID with the definition's env, ports, restart policy, `HostConfig.Mounts` (`{Type, Source, Target, ReadOnly}` from the frame's mounts; never `Binds`) and Compose labels (not started), stop the old `t=10` (304 counts), start and read the new identity, remove the old container without `v=1`. Rename and create run before stop so avoidable conflicts cost no downtime. The precondition decodes with pointers and is `denied`; the configuration refusals below are reported as codes of `protocol.UnsupportedCodes` (`undescribed` returns every one that applies, in vocabulary order; `image_config` for a differing `Cmd`/`Entrypoint`/`Healthcheck`/`WorkingDir`/`StopSignal`) with detail `unsupported: <codes joined by ", ">`, bounded to 256 bytes; an absent pointer-decoded field is still `the runtime did not report the container's full configuration` (`reported`). It is `denied` on changed identity, on an absent pointer-decoded field (`HostConfig`, `Config`, `NetworkSettings`, `Mounts`, `Privileged`, `AutoRemove`, `ReadonlyRootfs`; fail closed; other fields are compared by value), on a frame service without the `mounts` key (nil after decoding: a server older than mounts) against a container with any mount (`cannotExpress + "mounts"`, the pre-mounts rule; `[]` is a deliberate drop and allowed), on a frame bind with no `Mounts` entry of `Type` `bind` equal in `Source`, `Destination` and `RW` (`bind mount not present on the container`: binds are preserve-only; a bind the frame drops is allowed, and named volumes are not compared; paths compare byte for byte, so case matters, a trailing slash never matches because the wire requires clean paths, and symlinks are not resolved), and on the configuration listed here, which recreation would drop: mounts of any type other than `volume` and `bind`, anonymous volumes (a `volume` mount whose `Name` is 64 lowercase hex), `VolumesFrom`, a `VolumeDriver` other than `""`/`local`, mount options (a `Mounts` `Propagation` other than `""`/`rprivate` or a `Mode` with `nocopy`; in `HostConfig.Mounts` a bind propagation other than those or any recursion option, a volume `NoCopy`, `Subpath` or non-`local` driver), tmpfs, auto-remove, read-only root, privileged, capabilities, security options, devices, a PID mode other than `""`/`private`, an IPC mode other than the daemon defaults `""`/`private`/`shareable`, user, a non-empty runtime other than the daemon's `DefaultRuntime` (read once per run from `/info`; an unreadable default fails the first precondition), memory limits (`Memory`, `MemorySwap`, `MemoryReservation`), CPU limits (`NanoCpus`, `CpuShares`, `CpuQuota`, `CpusetCpus`), a PID limit, ulimits, sysctls, device requests, init, a user namespace mode, a cgroup parent, supplementary groups, extra hosts, DNS servers/options/search, links, a network mode other than `default`/`bridge`/`<project>_default`, networks other than exactly the accepted one, and a `Cmd`, `Entrypoint`, `Healthcheck` (absent, no test and `NONE` equal), `WorkingDir` or `StopSignal` differing from the old image's (read under `callBudget`). Log configuration (the daemon default, reproduced on the same daemon) and settings outside this list are not compared. Less than `replaceBudget` (`2*operationBudget + 4*callBudget`) before the deadline is `timed_out` at recheck with no call. A container on the Compose project network is recreated on it with `NetworkingConfig.EndpointsConfig[<project>_default].Aliases = [service]` so its Compose service DNS survives. A failed stop, start or identity read names the created container ID in the step detail; no identity is recorded and the old container is not removed. The first non-success ends the run; later steps are `skipped`; nothing is rolled back. With no Engine answer, a cancelled run (agent shutdown under the detached-context contract) is `unknown` and a deadline `timed_out`; a status is `failed`. Engine text never enters a result. `internal/agent/client`'s deployer calls it through `Options.Deploy` (`cmd/agent` and the built-in local agent both set it to `engine.Deploy` when a Docker socket is configured); see docs/agent-protocol.md, Deployment apply.
- The deploy `volume` step (`deploy_volume.go`): recorded once per distinct `Volumes` name, under the first service in plan order that mounts it, before that service's image or pull step. `GET /volumes/<name>` first, under `callBudget`: an existing volume the project owns (label `com.docker.compose.project` equal to the frame's project, driver `local`, no `Options`) succeeds with no create and may be mounted by any service. Any other existing volume is keep-only, like a bind: the step's service's old container must already mount it (else `denied` `volume is not owned by this project`), and every frame mount of it must match a `volume` mount on the same service's old container with the same `Name`, `Destination` and `RW == !ReadOnly` (else `denied` `volume mount not present on the container`): the step checks its own service, and each later service's precondition checks its own mounts of it (`deployRun.keepOnly`). So a revision cannot reach another application's volume or a `local` volume that is a host path by another name (`o=bind,device=...`), move such a volume to another service, or remount it read-write. A 404 is created only for a name starting `<project>_`; any other is `denied` `volume does not exist` (an `external` volume is never created). The create is `POST /volumes/create` with `{Name, Labels: {com.docker.compose.project: <project>, com.docker.compose.volume: <name without the "<project>_" prefix>}}`; only 201 succeeds, any other status is `failed` `volume create failed`; the 201 body must itself be owned, since Docker answers 201 with the existing volume when the name was taken meanwhile. No container has been touched at this step. Volumes are never removed.
- The deploy `pull` step (`deploy_pull.go`): `POST /images/create?fromImage=<host/repo>&tag=<digest>` with `X-Registry-Auth` (base64url, `base64.URLEncoding`, as moby decodes it and silently pulls anonymously otherwise, of `{"username","password","serveraddress":<host>}`) only when `Registries[Pull.Host()]` exists. Every pull, its inspect and its tag share one pull-phase deadline set once per run, `pullPhase(remaining) = min(remaining - replaceBudget, remaining*4/5)` (`deployRun.pullDeadline`); a pull with under `callBudget` of it left is `timed_out` with nothing sent, and each replacement keeps its own `replaceBudget` check before its recheck. The progress stream is read to EOF through `scanPullStream` (shared with `pullImage`, `maxPullLineBytes` per line), then `GET /images/<reference>/json` must report a full `sha256:` `Id` and a `RepoDigests` entry with a byte-equal digest and a repository equal after stripping `docker.io/` or `index.docker.io/` and then `library/` from both sides. Fixed `failed` details: 401/403 `unauthorized`, 404 `not found` (Docker Hub answers a private repository without a credential this way), other status or a stream `error` line `pull failed`, a mismatch `pulled image does not match`; no answer, a cut stream and an inspect status are classified by `outcomeFor`. When `Pull.Tag` is set, the verified `Id` is then tagged, `POST /images/<id>/tag?repo=<host/repository>&tag=<tag>` (201, anything else `tag failed`), before any container is touched, so the next plan and Compose resolve the tag to the update. The inspected `Id` is what `create` uses and the start identity check verifies; the identity carries `ImageDigest`. Neither daemon text nor the credential enters a step, result or log.
- `Client.Remove` tears down each `RemovalRequest` target in order: precondition (Id, Image and Created second must match, else `denied`; a 404 is a container already gone: `succeeded`, its stop and remove `skipped`, and the run continues), stop `t=10` (304 counts), then `DELETE /containers/{id}` with no query (never `v=1`; 404 counts; 409 is `failed` naming a dependency). Less than `operationBudget + 2*callBudget` before the deadline is `timed_out` at that target's stop with no mutating call. Networks and volumes are never touched. It reuses `deployRun.step`/`outcomeFor`, so skipping, outcome classification and Engine-text exclusion match `Deploy`; `Services` is always empty.
- `Client.Deploy`/`Client.Remove` take `started func()`, called once immediately before the first phase-two call (Deploy: inside the first `recheck`, after its deadline guard; Remove: inside the first `stop`, after its guard); a run that ends in phase one, or removes only containers already gone, never calls it.
- `ContainerImageDigests` follows a validated container identifier to its immutable image ID, then reads `RepoDigests`; it never resolves a tag. The API selects only its official repository and validates digest pins.
- `OpenExec` supplies the PTY runtime for both production agent adapters and the browser exec path. Callers enforce authorization, grants and admission before use. It requires full immutable container/image IDs, a running unpaused target, explicit user and bounded argv; it never adds a shell or requests privileged exec. Only a fixed TERM is supplied, and commands/output are not logged.
- `ExecSession` exposes raw combined PTY output, bounded 32 KiB reads/writes, resize and separate exit inspection. One reader/one writer may operate concurrently. Input/resize renew the 15-minute idle timer; output does not. An eight-hour absolute deadline and 20-second setup/control-call budgets remain effective. Close/context expiry closes the upgraded socket and unblocks I/O, but does not promise to kill the exec process. EOF is not an exit code; Inspect can run after Close and only returns an exit code when Docker confirms stopped. A failed attempted start is unknown and never retried.

- `pullImage` always sends `tag` alongside `fromImage`, defaulting to `latest` when the reference names neither a tag nor a digest. The Engine reads an empty `tag` as every tag in the repository, so omitting it would make "pull nginx" fetch the whole repository onto a managed host — the obvious thing to type doing the worst thing. The control plane refuses an untagged pull as well, so the record says what was actually asked for.
- `pullImage` sends no credential: credentials travel only with a deployment's pull step, so a registry that wants one is reported as a refusal (`credentialsMissing`) naming that route rather than a generic failure an operator would have to guess at. A pull reports some failures inside a `200` as a JSON line carrying `error`, so the progress stream is part of the answer: it is read to EOF line by line and each line decoded as JSON, never buffered to a byte ceiling and never matched as a substring. A stream that ends badly is `unknown`, never `succeeded` — believing a patched image is on a host that never got it is the one direction this must not fail in.
- `removeImage` refuses an image a container still uses rather than forcing it, which would leave running containers pointing at nothing. The reference rather than the resolved image ID is what gets deleted, because Docker untags a tag and deletes an ID; identity is pinned instead by `Expects.ImageDigest`, re-read immediately before the delete, so a tag that has moved since the decision is `denied` with nothing attempted. A removal arriving with no pin is refused: the control plane always sets one, and the agent is the last checkpoint before a root-equivalent socket.
- The HTTP client carries no `Timeout`: that timeout covers reading the body, so it would cut a pull's progress stream at twenty seconds however generous `pullBudget` is, and every pull of a real image would settle as `unknown` — toil for an operator, on the normal path. Every bound is a context deadline instead: the call's own (`operationBudget`, `pullBudget`) or `callBudget` applied by `bounded` when the caller named none, so the stated budget and the enforced one cannot drift apart.
- `protocol.ValidImageReference` is checked here as well as at the control plane. A reference becomes a path segment on a root-equivalent socket, and `url.PathEscape` is not allowed to be the only thing standing in its way — the same rule the container identifier already follows.
- `c.get` fails with a `statusError` carrying the daemon's status, and callers branch on the code. The formatted message quotes the request path, which holds a caller-supplied identifier, so matching `404` in it reads the name as readily as the status — a repository ending in `-404` is a legal reference — and would report a daemon fault as "this host does not have that image", asserting a host state nobody observed.
- Removal refuses a running, restarting or paused container rather than forcing it: Docker would oblige by killing the process first, and that is a second decision an operator should make explicitly. The delete carries no options, so named volumes and images survive; destroying data is its own action. A `409` from the runtime is reported as a refusal naming the dependency, not as a failure.
- `Operate` escapes the container identifier at every use, because it arrives in a request body and is concatenated into a URL addressed to the host's root-equivalent socket; the server constrains the grammar as well and neither check is allowed to be the only one. It runs one container action after re-reading the container: Docker has no universal resource version, so the precondition is operation-specific identity read immediately before acting (image digest, state). A precondition that no longer holds is `denied`, not `failed`, because nothing was attempted; `304 Not Modified` is `succeeded`, since the container was already where the caller wanted it.
- `Snapshot` reads `/info`, `/version`, `/containers/json?all=1`, `/images/json`, `/networks` and `/volumes` under Engine API `v1.41` (any newer daemon serves it), sorts every list so equal state serialises equally (each container's mounts by target, from the list's `Mounts`: `Type` `volume` reports its `Name`, `bind` its `Source`, anything else is kind `other`; `ReadOnly` is `!RW`; always a list, never `nil`; `protocol.Clamp` applies the `MaxMounts` cap), and truncates at `protocol.MaxContainers` (1000), `MaxImages` (1000), `MaxNetworks` (200), `MaxVolumes` (500), naming truncated lists in `Truncated`. Labels are capped at 32 entries of 256 bytes. Response bodies are read to 32 MiB at most.
- Before a snapshot leaves the host it is passed through `protocol.Clamp` (schema conformance and text safety) and `protocol.Shrink` (drops labels, then list tails, until the encoding fits `protocol.MaxSnapshotBytes`, naming what it dropped), so an honest agent never sends what the server would refuse. `bound` cuts on rune boundaries.
- Snapshot inventory never reads container environment. Targeted inspection receives Docker JSON containing configuration, but decodes only its allowlisted fields and never reports environment values or raw responses.
- `Stats` samples the named running containers with one-shot reads (`/containers/{id}/stats?stream=false&one-shot=true`, no daemon-side wait), computes the CPU share of one core from the delta against the previous call kept in memory per container (the first sample reports -1, meaning no interval yet), sums network bytes across interfaces, gives each container read five seconds, and caps a frame at `protocol.MaxSamples` (1000). A container that vanished between listing and sampling is skipped, not an error.
- `Engine` supplies `runtime_version` at enrollment; a daemon that is down at start is retried on the inventory schedule, not fatal.

- `Logs` streams one container's log. A container without a TTY has its output multiplexed by the daemon with an 8-byte header per frame, which is framing rather than log text and never reaches an operator; stdout and stderr are interleaved because they are one log to the person reading it. The reader's `sink` decides when enough is enough, so the line and byte bounds live with whoever is counting them rather than here. A log that ends is success, not failure: a stopped container's log ends immediately, and calling that an error would make every finished container look broken.

## Verification
- `KY_TEST_DOCKER_INSPECTION_IMAGE=alpine:3.24 go test -race ./internal/runtime/docker -run TestInspection` includes a disposable network-isolated fixture with secret canaries, read-only root and tmpfs; no pull occurs. CI runs it beside the real exec regressions.
- CI explicitly pulls `alpine:3.24` and runs the real exec regression in its isolated Docker runner.
- `KY_TEST_DOCKER_EXEC_IMAGE=alpine:latest go test -race ./internal/runtime/docker -run TestExecRealDocker` opts into a disposable network-isolated, read-only, capability-dropped container using an already-present shell image; no pull occurs and cleanup removes only that fixture. It proves explicit user, PTY input, resize and nonzero exit status.
- `KY_TEST_DOCKER_DEPLOY_IMAGE=alpine:3.24 go test -race ./internal/runtime/docker -run TestDeployRealDocker` commits the already-present image with a long-lived default command as `kyyarddeployfixture:local` and replaces a disposable fixture container running it without a command override on a fixture `<project>_default` network without pulling; cleanup removes the fixture containers by label, the image by tag and the network by name (idempotent: a leftover from an aborted run is removed before setup). The web fixture also mounts the named volume `kyyard_it_data`, written first by a one-off container, and a read-only bind of a test temp directory, and the frame carries both: it proves the volume step and bind precondition against a real daemon and that the file reads back from the new container, whose mounts are exactly that volume and the read-only bind; cleanup removes the volume. It proves that the new container runs, name/image/restart-policy/labels identity, that the new container lands on the project network under a service-name alias, that an env value reaches the container but never the serialized result, and that the old container is gone. With `KY_TEST_DOCKER_PULL_DIGEST` (alpine:3.24's repository digest; CI derives it after `docker pull`) a second fixture service is replaced from `docker.io/library/alpine@<digest>` pulled anonymously, proving `ImageDigest`, the pulled image's `RepoDigests` and the container's image ID. The local image is not removed first: on the containerd image store that drops the `alpine:3.24` tag too.
- `KY_TEST_DOCKER_DEPLOY_IMAGE=alpine:3.24 go test -race ./internal/runtime/docker -run TestRemoveRealDocker` builds the same kind of fixture as `kyyardremovefixture` with a named volume (`kyyardremovefixture_data`) and an anonymous one, removes the container, and proves the container is gone while the project network and both volumes remain (the anonymous volume is what fails if `v=1` is ever sent). Cleanup removes containers by label, the image, network and both volumes, before and after.
- `KY_TEST_DOCKER_DEPLOY_IMAGE=alpine:3.24 go test -race ./internal/runtime/docker -run TestRecheckRealDocker` runs a fixture container and, from the `started` hook, `docker update --memory 64m --memory-swap 128m` on it; the deploy must be `denied` at `recheck` and the old container still running under its name (fixture project `kyyardrecheckfixture`, cleaned by label, image tag and network name before and after).
- `go test ./internal/runtime/...` runs against a fake Engine (mapping, truncation) and, when `/var/run/docker.sock` is reachable, against the real daemon.
