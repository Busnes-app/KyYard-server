# API

## Purpose
Exposes HTTP REST routes, authentication endpoints, Single Sign-On callbacks, backup restore drill handlers, and static React PWA hosting.

## Ownership
Owns HTTP routing, request parsing, session cookie validation, CORS headers, and error response formatting.

## Local Contracts
- `ApplyInstaller` serializes native provider changes, validates the configured public callback and protected credential references, and calls the product-owned transactional store. Independent environment SSO/SCIM conflicts are refused. Managed provider readers load the committed immutable record directly, with no auto-provisioning or automatic account linking.
- Managed login verifies the current provider against the original attempt, exact verified issuer/subject and local owned binding before session issuance. Missing/mismatched app roles disable the identity and revoke grants atomically. Provider management APIs refuse installer-owned changes; public settings and admin extra settings omit protected references.
- `POST /api/installer/directory` accepts bounded 64 KiB `syncauth`-signed resources with explicit active assignment, app roles and canonical `meta.version`; the managed legacy `/api/sso/kysignon/sync` route delegates to the same boundary. It cannot use the legacy flat signature. Availability and revision fencing remain store-owned. `GET /api/installer/network` reports native `ClientIP`, transport-peer trust and scheme with `Cache-Control: no-store`.
- Linked local accounts with TOTP enabled must complete the existing one-use password-hash-bound TOTP/recovery challenge before SSO issues a session. The callback delivers the challenge in a no-store URL fragment; Login removes it from history immediately.
- Explicit self-linking: `GET /api/auth/sso` lists enabled provider IDs/names for a signed-in local account; `POST /api/sso/{provider}/link` requires its current password, normal CSRF and a five-attempt/minute account budget. It reuses the bounded five-minute PKCE/nonce/browser-bound login attempt with the original account, session hash and verified password hash. The callback verifies the provider identity, authenticates the same session again and calls store-owned `LinkSSO`; success retains the current session and redirects to `/settings?sso=linked`. Ordinary sign-in continues to refuse username collisions and never links by username/email.
- `POST .../endpoints/{endpoint}/run-yaml/preview` requires session-only `container.configure`, CSRF and a 12/minute preview budget; strict 128 KiB JSON carries at most 64 KiB YAML. Parse the bounded runtime-specific document, check every Deployment namespace against endpoint grants, and return transient full configuration with no dispatch or persistence. Fixed diagnostics contain positions/reasons only. Existing run routes retain all confirmation, identity, policy and audit gates. Native `run_manifest` additionally requires `kubernetes.manifests.run`; an older agent is 501 before recording or sending a command.
- `POST .../containers/{container}/updates/check` requires session-only `container.configure`, Docker runtime, fresh immutable inventory identity, CSRF and 12 attempts/minute. Resolve only the reported reference (a unique reported tag when the reference is the image ID) through `image.pull` credential/egress policy and the shared registry slot/deadline. Match local repository digests by canonical host/repository. Recheck identity and live configuration authority after remote work. Return a transient verdict/digests/time; `registry_error` additionally carries a closed `detail` (`unauthorized`, `not_found`, `rate_limited`, `private_destination`, `redirected`, `unavailable`). Preserve registry-policy refusals as `registry_not_configured`. Never return credentials or registry error text or dispatch a mutation.
- `POST .../endpoints/{endpoint}/inventory/refresh` uses tenant `endpoint.read` and CSRF, refuses service tokens (403, audited `denied`), requires `inventory.refresh` (501 for older agents) and a live agent (409 offline), then admits six requests per caller and endpoint and twenty per endpoint each minute (429; refusals spend nothing), dispatches to the agent and waits up to 35 s for a newer stored generation (200 inventory, 504 timeout). Polling reads reauthorize; inventory responses use `Cache-Control: no-store`. A queued frame alone is never success.
- `PUT .../applications/{application}/networking` accepts strict `{expected_revision, service_ips}` (a required map, empty to clear), delegates to `SetApplicationServiceIPs` under `application.edit`, and returns `201 {revision}`. Values stay server-side; normal CSRF, authorization and audit apply. Static-IP plans require `kubernetes.service_ips` at apply as well as planning; missing capability returns 501 on manual apply.
- `GET /endpoints/{endpoint}/containers/{container}/inspection` uses endpoint.read, fresh inventory and advertised container.inspect capability. Bind a 25-second request to the exact agent connection; admission is 2/endpoint, 1/actor/endpoint, 16/organization, 64/server, with 30 attempts/actor/minute. Recheck session/membership every second and immediately before returning; re-read target identity and require the same connection. Strict result parsing/validation permits only redacted fields plus a closed-vocabulary `unsupported` list; `configuration_verified` is true exactly when that list is empty. The route and plan-time inspection share `inspect`, a wrapper over `ask` (admission, grant, per-second recheck), which the configuration read shares too; the route keeps its rate limit and capability check, and `askSettled` (target re-read and status mapping) serves both HTTP routes. A grant is cancelled on the agent only when the server gave up before an answer. Disconnect/shutdown/HTTP cancellation ends the request; cancellation is best effort with an agent deadline. Results/commands are not persisted; no UI or deployment authority is added.
- `GET .../endpoints/{endpoint}/containers/{container}/configuration` (`configuration_handlers.go`) returns a Docker container's full configuration, env values included, under `container.configure`: service token 403 (denied row), `allowAttempt("configure:"+principal, 12, 1m)` 429, `CheckEndpointAccess` 403, `runtimeGate(dockerRoute)`, `ReadInspectionTarget`, `ContainerManaged` 409 `application_managed`, capability `container.configure` 501, no agent 409, then `readConfiguration` through `ask` on `s.configurations` (grant expiry min(deadline, now + `ConfigurationLifetime` − 2 s)), `askSettled`, `RecordConfigurationRead` (409 `application_managed` for a container adopted during the read). A `configuration.result` over `MaxConfigurationFrameBytes`, undecodable or failing `Validate` closes the socket; one failing validation against the target is 502. Values reach only the response (`no-store`); no audit detail or log line carries them (docs/agent-protocol.md, Container configuration).
- `POST .../containers/{container}/recreate` (`{expects:{image_id,created_unix,state}, spec, acknowledge_binds, confirm}`) and `POST .../endpoints/{endpoint}/containers` (run: `{spec, acknowledge_binds, confirm}`) (`recreate_handlers.go`, `handleDirectCommand`): service token 403, the shared `configure:` budget 429, `CheckEndpointAccess(container.configure)` 403, `runtimeGate(dockerRoute)`, strict 1 MiB body (`expects` exactly for a recreate), recreate target a full ID, managed 409 `application_managed`, a non-empty `spec.unsupported` 422 `configuration_incomplete`, `specInvalid` 422 `spec_invalid:<field>` (from `protocol.FieldError`), capabilities `deployment.apply` and `container.configure` 501, not connected 409 `endpoint_offline`, then the explicit one-service frame, `CheckDirectCommand` (before any registry call), `directImage`, `CreateDirectCommand`, deliver (failure: `FailDirectCommand`, 409 `deployment_not_sent`), 202 with the command. `CheckDirectCommand` and `CreateDirectCommand` get `AllowPrivileged` from `config.Container.AllowPrivileged` (422 `privileged_disabled`). `directImage` keeps the local image (`spec.image_id`, else the recreate target's) only when the inventory lists it with the spec's digest, or with no digest an ID equal to `spec.image.reference` or (for `spec.image_id` only, not the target fallback) a tag equal to it (KyYard creates containers by image ID, so their re-read reference is the ID); otherwise it pulls at the kept digest or the reference's current registry digest (`ResolveDirectImage` under `image.pull`, registry slot, `deployment.pull` else 501). `InvalidSpecError` maps to 422 `{code: invalid_spec, blockers}`; `ErrCommandInProgress` 409 `command_in_progress`; `ErrContainerManaged` 409 `application_managed`.
- `GET /applications/{application}/preflight` under the organization/environment prefix uses tenantRoute and application.read. Returns reference-only diagnostic findings; no deployment grant or mutation. Stale/incomplete container inventory or changed adoption is 409; absent adoption is 404.
- GET/PUT /applications/{application}/mapping within organization/environment reads and replaces service assignments. PUT accepts only instance_id, version, digest, confirm and bindings (service -> immutable adopted container ID), requires CSRF and application.adopt, and returns204. GET offers owned choices only; fresh complete inventory is required. Changed preconditions return409; unsupported services, duplicate/unowned IDs return400. No runtime dispatch.
- `POST /applications/{application}/revisions` within an organization/environment takes only `{expected_revision,compose}` and returns `{revision}` (201). Reuse bounded import parsing and fixed diagnostics, require CSRF and live `application.edit`; developer and administrator roles may save, operator/read-only may not. Full replacement saves desired state only; no runtime dispatch, secret reveal or implicit value carry-forward. Existing immutable revision GET reads history.
- `GET /applications/{application}/comparison` within an organization/environment returns an authorized read-only comparison for an adopted application. No instance is 404; unavailable/stale/incomplete inventory is an explicit availability field with no container observations. The response includes no arbitrary labels or environment values and cannot be submitted as a deployment approval.
- `GET /applications/{application}/updates` under organization/environment (`application.read`) returns the cached `store.UpdateCheck` `{instance_id, mapping_version, services}`; `services` is `[]` when nothing is adopted or checked. `POST .../updates/check` (CSRF, `application.deploy`: developers and administrators, not operators or read-only) runs a fresh check and returns the same shape. 409 `mapping_required` for an adopted but unmapped application, 409 `adoption_changed` when the mapping moved during the check, 409 `check_in_progress` while a check or an update plan for the same application runs: `guardApplication`, an in-memory `sync.Map` on `Server` (`imageChecks`) keyed `org/env/<canonical uuid>` shared with update plans (the handler parses the path ID, 400 when it is not a UUID, so another spelling cannot take a second slot), since one process is the supported deployment. `store.CheckImageUpdateAccess` authorizes before the slot is taken, so a caller without `application.deploy` gets 403 (404 for an unknown application), never 409. Once admitted it takes a registry slot shared with update plans: at most `registrySlotsPerOrganization` (2) per organization (`registryHeld` under `registryMu`, checked first, so one tenant cannot starve the others) and `registrySlotsTotal` (8, a `chan struct{}` on `Server`) server-wide; either limit reached is 429 `too_many_checks` "Too many registry checks are running; try again in a moment" with `Retry-After: 5`) and extends the response write deadline to `store.ImageCheckDeadline` + 5s, because the server `WriteTimeout` (15s) is shorter than a check may run. The handler passes `config.Security.EncryptionKey` and `config.Registry.AllowPrivate`; `registryResolver` builds one `registry.Client` per call with that service's `AllowPrivate`. An undecryptable credential is the generic 400. Responses carry digests and verdicts only, never a credential.
- `POST /applications/{application}/deployments` under organization/environment requires CSRF and application.deploy; body is `store.PlanRequest{instance_id,mapping_version,revision,confirm,update}`, checked against the current preflight's instance/version/revision/project — any mismatch is 409 `adoption_changed`. A clean preflight mints a `store.Deployment` (201) whose `correlation_id` is the request's `X-Request-ID`; any other blocker is 409 `preflight_blocked` with the blocker list and, when a service has blockers of its own, `services: [{name, blockers, unsupported}]`: service names and codes only, no reference or container identity. `GET .../deployments` (application.read) lists plans for the application; `GET .../deployments/{deployment}` reads one, 404 for a non-UUID or unknown id. Releasing an instance with a live unexpired plan is 409 `deployment_planned`; planning again replaces the prior plan rather than erroring. A non-empty `update` (service names) first runs `store.CheckImageUpdateAccess` (403 audited against `<app>/updates`, 404, 400 for a non-UUID) so a caller who may not deploy never holds or sees a slot, then takes the check's per-application guard (`guardApplication`, 409 `check_in_progress` while a check or another update plan for the application runs), then, after the plan-time inspections below (so a slow agent never holds a registry slot), takes a registry slot as the check does (429 `too_many_checks` with `Retry-After: 5` over the organization's 2 or the server's 8) and extends the write deadline as the check does, then passes the resolver, `config.Security.EncryptionKey` and `config.Registry.AllowPrivate`; each named service is pinned to the registry digest (`pull_reference`, `pull_digest` in the plan) and a registry failure is a `registry_*` blocker in the 409 `blockers`. A plan without `update` takes no slot. No credential reaches any body. `handlePlanDeployment` first reads `PreflightApplication` and the endpoint, and sets `MaxFrameBytes` from its capabilities with `maxFrameBytes` (320 KiB with `deployment.pull`, else 192 KiB), the same function apply uses; a body naming `max_frame_bytes` or `inspections` is 400 (strict decoding, the fields are `json:"-"`). Before `PlanDeployment`, `planInspections` inspects each mapped service's container (`PreflightApplication`'s `inspection_target`s) in plan order, one at a time, under `planInspectionBudget` (10 s) and one `inspection:` attempt per plan, each grant expiring at the earlier of the budget and `InspectionLifetime`; the fan-out does not gate on the latest revision's `executable` (the plan may be for an earlier revision; the store judges the revision planned); nothing is requested without both `container.inspect` and `container.inspect.verdict`; a failure of any kind leaves that container out of `PlanRequest.Inspections`. The response write deadline is extended by the budget, and an update plan extends it again for its registry work when it takes its slot. The fan-out stops once the budget is spent.
- `POST /applications/{application}/deployments/{deployment}/apply` under organization/environment requires CSRF and application.deploy; body is `{confirm}`. Order: read the plan, require the endpoint's advertised capabilities include `deployment.apply` (501 "Upgrade the host agent to enable deployments" otherwise) and, for a plan with any `pull_digest`, `deployment.pull` (501 "Upgrade the host agent to enable deployments that pull images"), require the endpoint connected (409 `endpoint_offline`), then `ApplyDeployment` (rechecks state/expiry/confirm/head/digest/mapping/endpoint, resolves values, CAS `planned → applying`) with the endpoint's frame cap: `protocol.MaxDeploymentRequestBytes` with `deployment.pull`, `MaxDeploymentRequestBytesLegacy` (192 KiB) without, a larger frame being 400 with the row still `planned`. If the built `deployment.apply` frame cannot be delivered to the live agent socket, `FailDeployment` marks the row `failed` and the response is 409 `deployment_not_sent` ("The deployment could not be sent to the endpoint": no socket or a full queue); otherwise 202 with the row. `ErrDeploymentInProgress` (a plan, a mapping or a second apply attempted while one applies) maps to 409 `deployment_in_progress`; a wrong confirm is 400.
- `POST /applications/{application}/removal` under organization/environment requires CSRF; body is `store.RemovalBody{instance_id,confirm}` (strict). Order: `ReadApplicationInstance` (404 when the instance is not this application's), require the instance endpoint's capabilities include `deployment.remove` (501 "Upgrade the host agent to enable application removal"), require it connected (409 `endpoint_offline`), then `RemoveApplication`, which enforces `application.destroy` (403 for developers and read-only) and the typed project (400), refuses a stale inventory (409 `adoption_changed`), more than 100 containers (409 `removal_too_large`) and an unadopted project container or unknown last apply (409 `preflight_blocked` with `blockers` `unadopted_project_containers`/`apply_outcome_unknown`), and inserts a `kind: "remove"` row already `applying`. A `deployment.remove` frame that cannot be delivered fails the row and answers 409 `deployment_not_sent`; otherwise 202 with the row. Its `deployment.result` settles through the same path as an apply; a result the store answers `ErrNotFound` (late or not this endpoint's) is logged as "late deployment result ignored" with the endpoint and deployment ID only. `GET .../deployments` rows carry `kind` and `endpoint_name`.
- Application `GET /{application}/adoption?endpoint=...&project=...` previews ownership; POST on that path accepts only `{endpoint_id,project,digest,confirm}` and atomically adopts the exact reviewed snapshot. DELETE takes `{instance_id,confirm}` to release ownership only. Both mutations require CSRF/live named permission and send no agent command. Stale, incomplete, offline or changed inventory is 409; adopted draft discard is 409. `GET /applications/instances` lists environment ownership summaries; `GET /endpoints/{endpoint}/applications` lists ownership with bounded container identities after endpoint authorization.

- `/organizations/{organization}/environments/{environment}/applications`: GET lists bounded drafts; POST accepts only `{name, compose}` and creates revision 1 without runtime dispatch. - Cluster workloads (`workload_handlers.go`, `endpoint_handlers.go`, `exec_handlers.go`; wire shapes, steps and codes are docs/agent-protocol.md, Kubernetes runtime), each after its permission and `kubernetesRoute`, then the capability (501), then the store (422 `namespace_not_granted` for a namespace not in the endpoint's `deploy_namespaces`, 404 for a target absent from the last inventory, 409 `application_managed` for a workload whose inventory `application` label is set), all before any frame: `POST .../commands` takes `workload.restart` and `workload.scale` (`container.operate`; scale needs `expects.replicas` 0..1000, every other action none) and `workload.delete` and `pod.delete` (`container.destroy`, `confirm` = the name) with `reference` `<namespace>/<kind>/<name>` and `kubernetes.workloads`; managed refuses delete only. `GET .../workloads/{namespace}/{kind}/{name}/configuration` and `POST .../apply` (`{resource_version, spec, confirm}`, confirm = the name) share `workloadGate`: service token 403, the `configure:` budget, `container.configure`, `kubernetes.workloads`; a pod kind is 400. - Workload image pins (`workload_images.go`): workload `apply` and `run` bodies take optional `pull` (container names). `pinWorkloadImages` first runs `store.CheckWorkloadFrame` so a refused request spends no registry budget, refuses `pull` with a `run_manifest` (400), takes one registry slot, shares one `store.ImageCheckDeadline` across every `Head`, resolves each distinct tracked reference once through `headDigest`, and rewrites the image to `repo:tag@sha256:...`. A registry failure or a digest-only image answers 422 `image_unresolved` (closed `detail`); store and policy refusals keep their codes. `POST .../workloads/{namespace}/{kind}/{name}/updates/check` (`handleWorkloadUpdateCheck`, `workload_update_handlers.go`) refuses service tokens, allows 12/minute on the shared image-check key, needs `container.configure`, a Kubernetes endpoint and kind deployment/statefulset/daemonset. A stored report older than 15 seconds may predate a rollout made outside KyYard, so `freshenInventory` first asks a connected agent advertising `inventory.refresh` for a new one and waits up to 10 seconds for it (at most 6 asks per endpoint per minute, apart from the operator's own refresh budget); otherwise the stored report is used as before (`TestWorkloadUpdateCheckRefreshesAnOldInventory`). Pods disagreeing on image, image ID or container set, or more than `protocol.MaxWorkloadImages` distinct containers, give `unknown` with no registry call; a managed workload answers `managed` with no registry call. `trackedReference` (a tag before `@` is tracked, a digest-only image is pinned) and `runningDigest` (containerd and `docker-pullable://` image IDs) decide the verdict under one shared deadline, and the inventory snapshot is re-read after the remote work (changed: `ErrAdoptionChanged`). `headDigest` and `registryDetail` are the one registry rule for the container check, the workload check and the pin.
- Browser exec uses the tracked `GET /endpoints/{endpoint}/containers/{container}/exec` WebSocket. Require the exact advertised Origin, active tenant session and `container.exec` before upgrading; a strict first message within ten seconds must supply the CSRF cookie value, explicit user/argv, immutable container/image IDs, size and confirmed inventory name before any runtime dispatch. Commit store authorization and intent first, then send a nonce-bound 60-second grant on that exact agent socket. Eight-frame queues close on overflow; admission is four per endpoint, one per actor/endpoint, 32 per organization and 128 server-wide. Limit attempts to ten per actor/minute before the audited authorization check. Revocation bypasses the control queue with a 500 ms direct socket write and closes that exact socket on failure. Ordinary cleanup queues best-effort cancellation under the normal control-write budget; an agent-reported close needs no cancellation. Browser writes stall out after five seconds; ready waits ten seconds; input idle is 15 minutes and absolute lifetime eight hours. Ping every 25 seconds. Membership events, agent loss and shutdown cancel immediately; session/account/membership/endpoint checks run independently every 250 ms with a 500 ms deadline, failing closed; input frames check cancellation without querying the store. Close audit uses a detached two-second budget and records actor, scope, target, user, duration and inspected exit status; missing exit remains unknown. Terminal bytes, argv and agent error text never enter audit records. Attachment closure does not promise process termination.
- `RunLocalDocker` runs the existing agent client in-process over a private loopback listener exposing only the authenticated agent-connect route. Derive a domain-separated local identity from the persisted instance key, resume generation from SQL, persist only the command ledger in `data/local-agent`, and join local connection handlers before store shutdown. Disabled/missing sockets never block the rest of the server. The private listener has its own 20/minute connection budget, selected by server wiring; public per-IP traffic cannot consume it, and both listeners require the same authenticated handshake.

- Additional-host commands use one `sudo docker run --pull always` with `--link`, persistent identity/socket mounts and default bridge. Default image is the official repository digest of the installed server container image, discovered through Docker using the server hostname and immutable image ID. Only the current official repository is accepted. - Metrics frames are limited to `protocol.MaxMetricsBytes`; the agent shrinks honest frames before sending, and an oversized frame receives `metrics_too_large` while the session remains alive. Sample-budget exhaustion likewise returns an error frame without ending the session.
- Provider login/callback routes `/api/sso/{provider}/login|callback` require an enabled configured provider. Existing environment providers keep IDs `kysignon` and `oidc`; configured providers get immutable random IDs. Sync/SAML metadata still require `KY_SSO_ENABLED`.
- `POST /api/sso/{provider}/backchannel-logout` is the OpenID Connect Back-Channel Logout receiver for any configured OIDC provider, enabled or not (an unknown or OAuth 2 provider is 400). Form `logout_token` (body ≤16 KiB), `Cache-Control: no-store`; 200 on success, replay or unknown subject, 400 `invalid_request` on any verification failure. A `sid` calls `EndSSOSession` (ending its sessions and pending MFA challenges) with a ten-minute fence (longer than the five-minute login and MFA windows); a `sub`-only token calls `EndSSOSubject` with cutoff `iat` + 1 s, which fences that provider subject for ten minutes (keyed by subject, so it also stops a first login still provisioning) and ends its sessions dated before the cutoff. Audited `auth.sso.logout` (platform scope, resource the provider ID). Anonymous: the provider's signature is its authority, and with no session cookie the CSRF check does not apply. Deliberately not rate limited: a KyIdentity restore sends one logout per login at once, and a 429 would exhaust its five retries. The callback and MFA completion carry the ID token `sid` onto the session and date it by the ID token's `iat` (`IssueSSOSession`; an MFA challenge stores the `iat`); a fenced login answers 401 with no session. `TestBackchannelLogoutEndsTheSSOLogin` covers sid, cross-provider scoping, fence (callback and MFA), subject-wide (a login after `iat` survives; a pending callback, a first login and an MFA completion holding an older ID token are refused), replay and ID-token confusion. `TestBackchannelLogoutFencesLateMFACompletion` covers a callback in flight that starts its MFA challenge after a `sid` or subject-wide logout: completing it is refused against the challenge's `sid` and `iat`. `TestBackchannelLogoutFetchesProviderMetadataOnce` proves repeated logouts, forged ones included, fetch discovery and the JWKS at most once.
- Admin-only `GET/POST /api/settings/sso` lists redacted provider configuration or creates a provider; `PUT /api/settings/sso/{provider}` rotates only the secret or changes availability without changing identity; `DELETE /api/settings/sso/{provider}` removes a UI-configured provider (existing sessions remain). The encrypted `sso_providers_enc` setting uses the deployment key with label `kyyard/sso/providers/v1`; it is included in the SQLite backup. Provider identity cannot be repointed to a different issuer. Local login is always available.
- SSO uses 5-minute, one-use server-side attempts (256 maximum with oldest-attempt eviction on admission, per-IP limit 10/minute), bound to provider ID and a random HttpOnly SameSite=Lax browser cookie, PKCE S256 and OIDC nonce. The reader disconnecting sends `log.cancel`, so the endpoint stops reading the host rather than running on for nobody. Two more things make the shape honest. Every line the control plane writes carries a token minted for the request and returned in `X-KyYard-Notice-Token`, because a container can print a line that looks like a notice but cannot know a token it never sees; and a bare carriage return ends a line, as the event-stream grammar says, so container output cannot escape its `data:` field and introduce events of its own. The response sets a write deadline of its own (`http.NewResponseController`), sized to the request's budget and refreshed on each write: the server's `WriteTimeout` is an absolute deadline for a whole response and would otherwise sever a stream mid-log with none of the promised markers. Authorization is re-asked every 25 seconds -- session and membership both -- and a membership change closes that reader's streams in the request that commits it. An oversized chunk ends that one stream rather than the session: the socket carries heartbeats, inventory and every command, so answering a data frame by closing it would turn an agent-side slip into an endpoint nobody can manage. Every socket transition closes the endpoint's readers exactly once: at the moment of displacement, because the successor has never heard of a stream the predecessor was serving and nothing would ever arrive on it again, and otherwise when the last live socket goes. The loser's unwind does not do it, or a successor's own readers would go with them.

- A `result` frame settles its command once (never a direct `container.recreate`/`container.run`, which only `deployment.result` settles), scoped to the endpoint that answers, so a late duplicate or an answer for someone else's command changes nothing. When a session ends, everything dispatched and unanswered becomes `unknown` with the reason: the connection going is not evidence the work did not happen, and nothing is retried on its own. A snapshot whose generation is not newer is logged and ignored.
- A `deployment.result` frame over `protocol.MaxDeploymentResultBytes` (160 KiB, exempt from the 64 KiB control cap) or one that fails to decode closes the socket with `CloseProtocol`, matching the incoming `deployment.apply` size check. Every decoded frame is passed to `SettleDeployment`, scoped to the sending endpoint, which reads an older agent's code-less result as `legacy` and validates it; on `ErrNotFound` it goes to `SettleDirectCommand` (a direct recreate or run). `ErrUnreadableResult` is dropped with a log line naming only the endpoint and the socket stays; `ErrNotFound` from both (a row this endpoint may not settle) is logged as a late result naming the endpoint and deployment ID; `ErrInvalid` or `ErrAdoptionChanged` (a result that does not fit the plan) calls `RefuseDeploymentResult` with "the host's result did not match the plan; inspect the host"; any other error logs the fixed text "settling deployment <uuid>: store error", never the error itself. `markOffline` also calls `AbandonDeployments`, so a session ending the ordinary way (not a protocol-violation close, which bypasses `markOffline`) turns its `applying` rows `unknown` immediately. A result echoing another deployment's `request_id` is `ErrInvalid` and takes the refusal path.
- `POST /api/agent/v1/enroll` is the agent-facing enrollment route: no session, no CSRF (no cookie), strict JSON `{token, public_key, proof, name, facts}` in base64url, per-IP limit 10/minute, `201 {endpoint_id, state, fingerprint, instance_fingerprint}`, `409 name_taken`, and every other refusal a uniform `401 Enrollment refused`. Unknown `/api/agent/` paths return JSON 404.
- `GET /api/organizations` lists the session user's own active memberships (`id`, `name`, `role`) for the organization selector. It is identity-scoped, not tenant-scoped: it never lists another user's organizations and platform administrators without membership get an empty list.
- Platform administration (`admin_handlers.go`, `requireAdmin`, CSRF on POST, `strictJSON` with a 4 KiB cap, `Cache-Control: no-store` on every response): `GET /api/admin/organizations` returns `[{id, name, created_at, members}]` by name; `POST` takes `{name, admin_user_id}` (name 1..64 characters, `protocol.CleanText`-stable; `admin_user_id` must match `^usr_[0-9a-f]{24}$`, else 400, so it cannot forge audit details) and calls `CreateOrganizationWithAdmin` with `id = "org_" + crypto.RandomHex(12)`; 409 `organization_exists`, 404 `user_not_found`, 409 `user_inactive`. `GET /api/admin/users` returns at most 500 users as `[{id, username, display_name, role, status, sso_provider, created_at}]` by username, never hash, TOTP or recovery fields. `POST` takes `{username, display_name, role}` (`^[a-z0-9._-]{3,64}$`, display name 1..128 CleanText-stable, role `user` or `admin`; 409 `username_exists`, checked case-insensitively because login matches `LOWER(username)` while the column is unique only by exact case; a lookup error other than not-found is a 500, never a fall-through) and creates a local, active user with `MustChangePassword` and a 24-character `[A-Za-z0-9]` temporary password from `crypto/rand`, hashed with `password.Hash`; the plaintext appears only in the 201 body, never in a log, audit row or later read. Audit rows are `scope: "platform"`, actor the admin: `organization.create` (resource the org ID, details `admin=<user id>`) and `user.create` (resource the user ID, details `role=<role>`); a refusal (the username pre-check or the store) writes a `result: "failure"` row with the requested name as resource and `refused=<code>` in details.
- Membership writes take `{role, status?}` (status defaults to `active`); the user ID comes from the path and must already exist and share an organization with the actor, unless the actor is a platform `admin` (one identical 404 otherwise). A successful write ends that user's log and exec streams in this organization only (`TestMembershipChangeClosesOnlyThatOrganizationsStreams`). `409 {code: last_administrator}` means the change would leave the organization without an active administrator, including an administrator demoting, disabling or removing themself.
- `tenantRoute` authenticates unrestricted sessions, derives actor and correlation ID server-side, and sends `X-Request-ID` plus `Cache-Control: no-store`. Handlers pass explicit URL scope to authorized store methods; clients cannot supply actor, organization or arbitrary update fields in JSON. Existing Origin/CSRF/body limits apply.
- Every tenant JSON body goes through `strictJSON` (unknown fields and trailing documents rejected). Environment create/update accepts only `{name}`; lists accept nonnegative `offset` and `limit` 1–200 (default 50). Store errors map to generic 400/403/404/409/500 responses. Request parsing/authentication/CSRF failures occur before the transactional tenant audit path.
- `policies.go` is the update-policy scheduler, `RunPolicies(ctx, done)`: a one-minute tick under the `policyTick` mutex (no tick while stopping) reads `SchedulePolicies`, records each missed window (`skipped_missed`, or `skipped_busy` when this process passed the open window over as busy: such an occurrence is remembered and recorded on the first tick after it ends, whatever window the schedule then lists, and forgotten after a day only if it cannot be recorded), then starts each due policy in its own goroutine when its endpoint holds no `applying` or unexpired `planned` deployment and `admit` allows (one run per endpoint, two server-wide). A run opens its row first (`BeginPolicyRun`), acts as `created_by` under a fresh correlation ID with every step re-authorized in the store (`CheckImageUpdateAccess`; `holdApplication`, else `skipped_busy` `check_in_progress`; `waitRegistrySlot` up to 30 s, else `skipped_busy` `too_many_checks`; `CheckImageUpdates`; `inspectForPlan`; `PlanDeployment` with the `update_available` services, in `apply` mode only once `Connected` (else `failed` `endpoint_offline`, no plan); in `apply` mode `ApplyPolicyDeployment` (a changed or deleted policy is `planned` `policy_changed`; a deleted policy's `FinishPolicyRun` is `ErrNotFound`, logged once, nothing recorded) and `deliver`, `FailDeployment` with `not_sent` when the frame cannot be queued) and ends in `FinishPolicyRun`. `ErrForbidden` anywhere pauses (`paused`); other refusals are `failed` with `not_adopted`, `mapping_required`, `adoption_changed`, `deployment_in_progress`, `endpoint_offline`, `invalid` or `error`; blockers are joined whole within 255 bytes. A run shares its creator's inspection rate budget (`inspection:<actor>`, 30 per minute) with that person's manual inspections; a run that cannot inspect is `blocked` `inspection_unavailable`. Runs use `context.WithoutCancel`; `done` closes only after the loop stops and every run has finished. A panic inside a run's goroutine is recovered there: logged as `policy run <policy id> panicked: <value>` with no frame content, the row finished `failed`/`panic` when it had already opened (silent otherwise), and the goroutine's own deferred `release`/`runs.Done` still run, so one bad run neither wedges the endpoint's slot nor takes the tick loop down (`TestPolicyRunPanicRecoversAndRecordsFailed`, exercised through the test-only `panicHook`). `guardApplication`, `acquireRegistrySlot` and `planInspections` are the HTTP wrappers of `holdApplication`, `takeRegistrySlot` and `inspectForPlan`.
- `validations.go` is the health-validation loop, `RunValidations(ctx, done)`: a `store.ValidationPoll` tick under its own mutex (no tick while stopping) first decides every named, undecided rollback from its deployment (`DecideNamedRollbacks`, so a failed outcome write cannot leave the policy active), then reads `PendingValidations` and advances the rows on `validationWorkers` (4) goroutines, at most one row per organization in flight (the store already cut each organization to `store.PendingValidationsPerOrg` rows), organizations round-robin and each organization's rows oldest first, each row reading the clock when it starts (a stalled agent holds one worker, never all); the rollback runs on the row's worker and the tick returns once every started row finishes. Each row: after `ValidationGrace` it needs `container.inspect.health` (else `unverifiable`) and a connected agent (offline, at the baseline or later, it waits), inspects each settled container the store has not placed as gone or replaced through `observe` as `system-validation` under the plan's 10 s budget, takes the baseline (`BeginObservation`, only before `observe_until`: a row still in grace at or after it finishes `unverifiable` `the host could not be observed`), judges every poll with `store.Judge`, and past `observe_until` + `ValidationGrace` without a complete observation records `the host could not be observed`. A released instance is `changed`. When `FinishValidation` reports a decision due (or the row was left awaiting one), the rollback runs under `context.WithoutCancel` as the policy's `created_by` with a fresh correlation ID: `RollbackTarget`, `Connected` (else `failed` `endpoint_offline`, no plan), `inspectForPlan`, `PlanDeployment` with `PinImages`, `MarkRollbackPlanned`, `ApplyPolicyDeployment` with no run (a rollback is never automated) and `deliver` (`FailDeployment` and `not_sent` when unsent), then `MarkRollbackOutcome` pauses the policy. `done` closes only between ticks. `performPolicyRun` passes its run to `ApplyPolicyDeployment` (which makes the apply automated) and names its deployment on the run (`AttachPolicyRunDeployment`) before the frame leaves; when naming fails it sends nothing, fails the deployment and finishes the run `failed` `error`. Tests route every store call through `faultyTenancy`, installed before the agent connects (`newValidationHost`), never swapped under a live connection; `validationHost.flood` writes a backlog straight into the database through `planHost.db`. A cluster row without `kubernetes.inspect` finishes `unverifiable` with `ValidationDetailNoInspect`; with it, each service is inspected by a `Workload` target built from the settled identity (namespace, name, UID) and observed with the settled generation.
- `policy_handlers.go`: `GET|PUT|DELETE .../applications/{application}/update-policy`, `POST .../update-policy/resume`, `GET .../update-policy/runs?limit=` (default 20, 1..100). `GET` answers 404 with no store error when there is no policy and otherwise the policy's fields plus `runs` (latest 20) and `next_occurrence` (UTC, null while paused). `PUT` is strict JSON `{mode, timezone, weekdays, start_minute, end_minute}`, 201 created / 200 edited; `tenantError` maps the four field errors to 400 `invalid_mode`, `invalid_timezone`, `invalid_weekdays`, `invalid_window` and `ErrPolicyNotPaused` to 409 `policy_not_paused`.
- The agent socket knows the endpoint's runtime (`agentConn.runtime`). A `hello` whose capabilities do not fit it (`protocol.CapabilitiesFit`: a Kubernetes endpoint names only the runtime-neutral `inventory.refresh`, `kubernetes.inventory`, `pod.logs`, `kubernetes.deploy`, `kubernetes.claims`, `kubernetes.service_ips`, `kubernetes.remove`, `kubernetes.inspect`, `kubernetes.workloads`, `kubernetes.workloads.run` and `pod.exec` (so `deployment.pull` from a cluster is refused), a Docker endpoint accepts `inventory.refresh` but none of the Kubernetes capabilities) is answered `error {code: capability_mismatch, runtime}` and closed with `protocol.CloseProtocol`, pending endpoints included; nothing is stored. A snapshot of the wrong shape (`protocol.CheckRuntimeShape`) is answered `error {code: snapshot_rejected, runtime}` and the session continues, like `snapshot_too_large`.
- `runtimeGate(kind)` (`runtime_gate.go`; `runtimeEndpoint` also returns the endpoint) reads the endpoint under `endpoint.read`. `kubernetesRoute` answers the same 409 for a non-cluster endpoint: workload commands, workload configuration, apply and run, pod exec. `dockerRoute` answers 409 `runtime_unsupported` for a non-Docker endpoint before any capability check: commands, removal preview, inspection, configuration read, recreate and run, container logs, exec (before the upgrade), adoption preview and adoption by the named endpoint. `applicationRoute` (service mapping by the body's `endpoint_id` or the instance's endpoint, plans by the instance's endpoint) accepts both runtimes; the store holds each instance to its endpoint's runtime (`ErrRuntimeUnsupported`), and apply and application removal refuse a plan or instance of the other runtime's shape (a namespace on Docker, none on a cluster) with the same 409. Every gated route checks the action's own permission first, so a member without it gets 403 and a `denied` audit row, never the runtime: exec after its per-actor rate limit (`CheckEndpointAccess(container.exec)`), configuration read, recreate and run after theirs (`CheckEndpointAccess(container.configure)`), commands after parsing the body (`CheckEndpointAccess` with `store.CommandPermission(action)`; an unknown action is left to the store), adoption preview, adoption and service mapping through `adoptionGate` (`CheckApplicationAccess(application.adopt)`); inspection's and the removal preview's permission is `endpoint.read`, the gate's own endpoint read. The mapping PUT reads the instance only when the body names no endpoint. Apply and application removal pick the capability with `runtimeCapability` (the plan's or instance's shape against the endpoint's runtime, 409 on a mismatch), and a cluster plan runs no container inspection. Endpoint, inventory, samples, rollups and the command list stay readable.
- On a Kubernetes instance, a plan runs as an image update does (`CheckImageUpdateAccess`, the application guard, a registry slot), since the store resolves every image at the registry; apply requires `kubernetes.deploy`, plus `kubernetes.claims` for a plan with claims, and removal `kubernetes.remove` (501 without), `maxFrameBytes` is the full cap for `kubernetes.deploy`, and the frames are the store's (`deployment.apply` with `kubernetes`, `deployment.remove` with `kubernetes` and `services`). `ErrNamespaceUnknown` is 400 `namespace_unknown`; a namespace revoked between plan and apply is `409 preflight_blocked` with `k8s_namespace`, and a policy run records it `blocked`.
- `GET /endpoints/{endpoint}/pods/{namespace}/{pod}/logs?container=&tail=&search=&follow=&download=&timestamps=` validates the names as DNS-1123 (`protocol.PodTarget`, 400), requires a Kubernetes endpoint (409 `runtime_unsupported`), the stored `pod.logs` capability (501) and `container.logs` through `store.OpenPodLogTarget`, then shares `streamLog` with the container route: same tail default and ceiling, caps, notice tokens, SSE and download shapes, `log.cancel` and access recheck; `log_streams.go` is unchanged. The frame carries `LogRequest.Pod` and no container ID; an empty `container` lets the agent choose the only one or refuse with `unknown_container`.
- `migration_handlers.go`: `POST|GET|DELETE .../applications/{application}/migration`, `PUT .../migration/choices` (`store.MigrationChoices`: `volumes` and `acknowledged`), `POST .../migration/analyze|destination|validated|cutover`. Start first reads `store.ReadOpenMigration` (409 `migration_open` when one is open); choices and analyze read the open migration through `sourceMigration` (`ReadOpenMigration`, under `application.migrate`, so a member who may not migrate gets 403 and a denied audit row, never 404) and refuse any status but `analyzed` (409 `migration_state`). All three then read `store.ReadMigrationSource` (under `application.migrate`, so nobody else causes an inspection), refuse a namespace the cluster does not grant (400 `namespace_unknown`) and invalid choices (`store.CheckMigrationChoices`) before any inspection, then read `PreflightApplication` for the mapped containers' targets and `planInspections` (the plan's primitive and its `inspection:<actor>` budget; observations are used once and dropped), run `migration.Analyze` in the handler and pass `store.MigrationAnalysis` to one store write. Choices and analyze act on the source's open migration only (a destination's `GET` answers `role: destination`, and its writes 404). Abandon answers the migration plus `destination_kept`. New `tenantError` codes: 409 `migration_open`, `migration_not_ready`, `migration_state`, `migration_stale`, `application_name_taken`, `destination_name_too_long`, `inventory_stale`; 400 `storage_class_unknown`, `size_invalid`, `volume_unknown`. `manifestNote` asks the operator to re-apply the regenerated manifest after an upgrade.
