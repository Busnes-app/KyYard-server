# Agent

## Purpose
The KyYard agent side of the fleet: `protocol` (wire helpers shared with the control plane) and `client` (durable identity, enrollment, connection loop). The binary is `cmd/agent`.

## Ownership
Owns signed-message preimages, frame types, the agent's identity file, enrollment against `/api/agent/v1/enroll`, and the outbound WebSocket session against `/api/agent/v1/connect`. The control plane side (handshake, registry, state transitions) is owned by `internal/api` and `internal/store`.

- Commands run off the session loop, at most `maxInFlightCommands` (4) at once, answering through a buffered channel the loop selects on. A pull is bounded by the network rather than by the daemon, so running one inline would cost heartbeats: any principal holding `image.pull` could push an endpoint offline and keep it unmanageable for as long as the pull ran. Past the limit a command is `denied` immediately rather than queued — an answer now beats an answer later, and a queue lets one caller spend the agent's memory. Image actions draw from a reserve of their own (`maxInFlightImageCommands`, half the limit) as well as a general slot: a pull waits on a remote registry rather than on the daemon, and without the reserve four of them — four ordinary large images, or one caller holding nothing but `image.pull` — would occupy every slot and make an administrator's emergency stop come back `denied` for minutes. Moving that outcome from the heartbeat path to the command path would not have been fixing it. A command already in the ledger replays its stored answer before the limit is consulted: the server re-dispatches precisely when it never heard the first result.
- The ledger and the limit are created in `Run`, above the reconnect loop, and belong to the agent rather than to one connection. A command outlives the socket it arrived on and sessions end at the server's choosing (shutdown, a read gap, duplicate eviction), so per-session state would grant four more in-flight commands with every redial and let a stale ledger serialise itself over the file, erasing what the new session recorded. A worker hands its result over through `deliver`, which gives up when the session context ends: the slot must come back even when the loop has gone, or each drop would cost a quarter of the agent's capacity permanently. Nothing is lost, because the answer is already in the ledger. `Options.Operate` takes the session's context, so a dropped socket cancels work nobody is waiting for (and `Options.Logs` likewise) — a runtime call that ignores cancellation still holds its slot until it really ends, which is the honest accounting.

## Local Contracts
- Inspection uses inspection.open/result/cancel with endpoint/actor/nonce/immutable target and a 25-second expiry. Both Docker adapters advertise container.inspect and container.inspect.verdict (`protocol.CapabilityContainerInspectVerdict`: answers carry the verdict; plans require it) when configured. Two workers per Run remain occupied across reconnect until they finish; runtime calls never block heartbeats. Grants are consumed until expiry (1,024 ceiling), replay/pending/cross-connection requests refuse. Validate redacted results on both sides, cap frames at 32 KiB, suppress runtime errors, and discard cancelled results. Counts replace paths/names; `unsupported` lists codes from `protocol.UnsupportedCodes` (at most `MaxUnsupported`, 32, distinct) and `configuration_verified` is true exactly when it is empty; inspection grants no deployment authority.
- The server’s built-in local agent reuses `Run` with a domain-separated identity derived from its instance key, SQL inventory generation and no key rotation. `Options.CommandDir` separates its durable command ledger from identity-file persistence; ordinary agents continue using `IdentityDir` for both. No embedded private identity or ephemeral loopback address is written to disk.
- `cmd/agent` prints the current public-key fingerprint at startup, derived from its persisted private key, so operators can compare it before approval. Tokens and private keys stay out of logs. The published server image includes this binary at `/app/kyyard-agent`. `--enroll-only` creates the identity, prints the fingerprint and exits; it refuses an existing identity with its endpoint/server named, so a fresh token cannot silently reuse a different tenant enrollment. `--link` accepts the generated HTTPS URL with a token fragment, enrolls and continues in one process without stdin. Saved identities retain only an enrollment-token hash, atomically with the identity; restart with the original link reuses it, and another link refuses the volume. The link remains in Docker arguments/shell history, but never agent logs or the identity file. Legacy stdin and `--enroll-only` remain supported.
- `protocol.ExecSpec`, `TerminalSize` and `ExecStatus` define the runtime exec boundary: immutable Docker IDs, explicit user, direct argv (64 arguments / 8 KiB total), dimensions 1–512, 32 KiB I/O chunks, 15-minute input-idle and eight-hour absolute lifetimes. Exec transport frames and `Options.Exec` are wired by the standalone and built-in Docker agents; a configured adapter advertises `container.exec`. The initial authenticated hello may be approved, active or offline: all are eligible for a server-authorized grant after inventory makes the endpoint active. Pending and unknown states remain ineligible.
- `protocol.DeploymentRequest`/`DeploymentResult` define the deployment apply boundary: `TypeDeploymentApply`/`TypeDeploymentResult`, `CapabilityDeploymentApply`, `CapabilityDeploymentPull` (`deployment.pull`: the agent runs a service's `Pull`; the server sends no pull without it), frames capped at `MaxDeploymentRequestBytes` (320 KiB; `MaxDeploymentRequestBytesLegacy`, 192 KiB, for an agent without `deployment.pull`) and `MaxDeploymentResultBytes` (160 KiB, proven to hold the largest result `Deploy` produces), an `IssuedAt` (`issued_at`, the server's clock at build) within `MaxClockSkew` (5 minutes) of the reader's clock, else `ErrClockSkew`, which the adapter and the deployer answer `failed` code `clock_skew` with no step and no ledger entry, and a deadline in `(IssuedAt, IssuedAt + DeploymentLifetime]` and at most `DeploymentLifetime` (15 minutes) past now, and 1..`MaxDeploymentServices` (100) services in plan order. Both requests carry a required `RequestID` (`request_id`, `ValidRequestID`: `^[A-Za-z0-9_-]{1,64}$`), the plan's audit correlation ID. `RemovalRequest` carries the same `IssuedAt`, skew bound and deadline rule. `Validate` refuses a past or overlong deadline, duplicate service/container names, `Replaces.ContainerID` or `(HostIP, Host, Protocol)` port bindings within or across services (host IP normalised with `netip`: `""` and `0.0.0.0` are one IPv4 wildcard, `::` a separate IPv6 one), a malformed project/service name, a bad restart value, out-of-range ports and env past `MaxDeploymentEnvEntries`/value/total bytes. A service carries either a full `ImageID` or a `Pull` (`ImageID` empty; `Reference` a valid reference with a registry host, `ImagePull.Host()` reading the host as written, and a `sha256:` digest equal to `Pull.Digest`; an optional `Tag`, a tag reference with no digest and the same host and repository as `Reference`, which the adapter tags the pulled image with). `Registries` maps host to `RegistryAuth` for at most `MaxRegistryAuthHosts` (16) hosts, each one some service in the frame pulls from, with a non-empty UTF-8 secret without NUL of at most `MaxRegistryAuthSecretBytes` (4096) and a username of at most 255 bytes; the credentials are never logged. `DeploymentService.Mounts` has no `omitempty` and `nil` is invalid. A service carries at most `MaxMounts` (32) `Mounts`, each `MountVolume` (source a volume name, `[A-Za-z0-9][A-Za-z0-9_.-]{1,128}` so a resolved `<project>_<name>` fits) or `MountBind` (source an absolute, `path.Clean` path), target absolute, clean, not `/` and unique per service, paths at most `MaxMountPathBytes`, unchanged by `CleanText` and free of format characters (bidi, zero-width), so a path displays as it is. `Volumes` lists at most `MaxDeploymentVolumes` (64) distinct names, exactly the set of names the services' volume mounts use, so every mounted volume passes the agent's ownership check. `DeploymentResult.Validate` bounds steps at `MaxDeploymentResultSteps` (8×`MaxDeploymentServices` + `MaxDeploymentVolumes`: eight per service with `recheck`, plus one per volume) and identities at `MaxDeploymentServices`, each identity as an `InspectionTarget` with an optional `ImageDigest` (`sha256:` + 64 hex, the pulled repository digest), accepts steps `pull`, `volume` and `recheck` beside `image`, and checks outcome codes: a `succeeded` or `skipped` step carries no code and no detail, any other step a step code whose detail has the shape the code allows (`stepCodes`: `unsupported` one to 32 distinct `UnsupportedCodes` joined by `,`, `identity_unreadable`/`identity_unverified` a 64-hex ID, `runtime_status` `[1-5][0-9]{2}`, every other code empty), within `MaxDeploymentStepDetailBytes`; `DeploymentResult` has no free `Detail`; a result's `Code` is set exactly when its outcome is not `succeeded`, from `step_failed`, `clock_skew`, `invalid_request`, `wrong_endpoint`, `busy`, `restarted`, `unreadable`; `legacy` is in both sets and only the server's store assigns it. `RequestID` on a result is optional (empty from a binary built before it) and otherwise must be valid; the protocol never fills a missing code. The Docker adapter (`internal/runtime/docker`) executes `Deploy`; the transport below sends and receives the frames.
- `deployer` (`client/deployments.go`) is created in `Run` beside the command ledger and runs `Options.Deploy` (`deployment.apply`) and `Options.Remove` (`deployment.remove`, a `protocol.RemovalRequest`) through one runner (`handleApply`/`handleRemoval` decode, `run` gates and executes), one at a time agent-wide across both kinds, on `Run`'s root context, never the session's. Each capability is advertised only when its option is set (`deployment.pull` beside `deployment.apply`); either frame past `MaxDeploymentRequestBytes` closes with `protocol_error`; pending sessions ignore both. Everything below applies to both kinds. A frame this agent cannot attribute to a valid deployment — undecodable JSON, or `Deployment` not a UUID (`protocol.ValidDeploymentID`) — gets no answer at all and is not logged beyond a fixed `deployment frame ignored: no valid deployment id`: `DeploymentResult.Validate` requires a UUID, so there is no valid result to send, and the server never sends such a frame; if one somehow arrived, it settles on the server as `unknown` when the connection is abandoned. Every other answer carries the frame's `request_id` when `ValidRequestID` accepts it (else empty) and a result code, never a sentence: a frame with a valid deployment UUID that otherwise fails `Validate`, and a frame for a kind this agent has no runtime for, `denied` `invalid_request`; clock skew `failed` `clock_skew`; another endpoint's `denied` `wrong_endpoint`; a second run `denied` `busy`. After `Validate` accepts a frame the deployer logs `deployment <id> (request <request_id>): received`, then `started` from the `started` hook and `finished <outcome>` when the result is recorded; the request ID is echoed on the run's result whatever the runtime returned. A request carrying the ID of the running deployment gets no answer, checked right after decoding and before `Validate` (a refusal, even for a re-sent frame past its deadline, would settle the live row). A known ID replays its recorded result, also checked before `Validate`, so a re-sent frame past its deadline is answered from the ledger. Invalid (with a valid UUID), foreign-endpoint, no-runtime and busy requests are answered `denied` and not recorded. The run drops its references to the env values and the `Registries` credentials once `Deploy` returns (the process heap is not scrubbed) and the request is never logged; the ledger holds results only, never the frame or a credential. A result failing `DeploymentResult.Validate` or naming another deployment is replaced by `unknown` `unreadable` before it is recorded. On shutdown `Run` waits (`deployer.wait`) for an in-flight run to record its result before returning, bounded by the request deadline (at most 15 minutes) and, for the built-in local agent, by the server's shutdown budget (`backupWaitTimeout`). Each result is written durably to `<CommandDir>/deployments.json` (0600, fsynced temp + rename + directory fsync, 24 h, 20 entries) and the slot is freed before it is sent. The result goes to the session current when the run finishes (each non-pending session attaches after its first inventory and detaches on return); with none connected, the next session's re-send carries it. Every non-pending session re-sends the whole ledger after attaching, blocking on the session rather than dropping past the outbound buffer. The runtime's `started` hook makes the deployer write `{started, request_id}` for the ID durably before the first phase-two mutation. On load, an entry with `started` and no result becomes `unknown` `restarted`, carrying the recorded request ID, and is re-sent, and a re-sent frame for it replays that result; an entry with neither a start nor a result is dropped. Pruning never drops a started entry and re-sending skips it while its run is live.

- `protocol.Preimage` length-prefixes the context and every field with 4 bytes; the three contexts are enrollment, connection and rotation and no signature verifies across them. `AuthPreimage` binds endpoint ID, nonce, the host the agent dialed and the protocol version.
- Frames are JSON `Envelope`s with `v: 1`; the connection lifecycle uses `challenge`, `auth`, `hello`, `heartbeat`, `inventory`, `enrollment.approved` and `error`. Close reasons are the constants in `messages.go` and are the agent's only signal for terminal versus retryable failures.
- Identity lives in `identity.json` under a 0700 directory as a 0600 file written atomically and durably (the temp file and the directory are fsynced before the rename returns, so a rotation offer is never announced for a key a power loss could erase): endpoint ID, Ed25519 private key, the pinned instance fingerprint and the server origin. Enrollment uses stdin or the HTTPS link once; plaintext tokens are never written to the identity volume.
- `checkServerOrigin` gates both enrollment and connection: https anywhere, http only to loopback, no credentials/query/fragment; `Enroll` refuses before generating a key or sending anything. `Enroll` checks the server echoed our fingerprint before saving; a challenge whose instance fingerprint differs from the pinned one is `ErrInstanceChanged` and stops the loop.
- Rotation (`--rotate-every`, default 30 days, 0 disables; `RotatedAt` is set at enrollment so the first offer lands one interval later): at the start of a session past the interval the agent mints a key and persists it as pending; if that write fails nothing is sent and the session errors, because a key held only in memory would strand the agent once acknowledged. Then it sends `identity.rotate` signed by the current key and keeps authenticating with the current key. An offer unacknowledged for eight days (`PendingSince`; one day longer than the server's seven so the agent forgets strictly after the server stops accepting, whatever the clock skew) lapses: its bookkeeping is cleared so a fresh key can be offered, but the key material is retained (`LapsedPrivateKey`) until the server records a new offer; if the server refuses the fresh offer as `rotation_pending` the lapsed key is restored as pending, and a `key_retired` refusal switches to the next candidate. Every key the server confirmed it holds (`PendingRecorded`, `LapsedRecorded`, carried across the lapse) is tried before any key it never answered for, because a session killed between saving an offer and reading the answer leaves a key the server may never have recorded, and an unknown key draws exactly the answer a revoked endpoint draws. That answer, `identity_revoked`, stays terminal for a key that has authenticated before: the server also sends it for a signature mismatch or a store error, and a rotation window must not turn either into a lost identity. Mid-walk (`RecoveryAttempt` above zero) the key in hand has only ever been refused, so each remaining candidate still gets one try; a genuinely revoked endpoint refuses them all and the agent stops. The walk is an index held only in memory (`RecoveryAttempt`, never serialised), not a promotion: no key is moved or overwritten while it runs, so a `Host`-rewriting proxy or a store outage that refuses every candidate leaves the stored identity as it was and the key that works is still on disk when the fault clears. An exhausted walk resets the index, and so does a restart, so the next cycle begins at the identity's own key rather than the last one refused. Only a server accepting a candidate commits it, because that answer is the only proof the old key is retired; the handshake then adopts it and drops the rest. A `key_retired` close of a live session switches at once. `identity.rotated` from the server, or a connect refused with `key_retired` while a pending key exists, promotes the pending key and reconnects after a one-second pause (so the server has freed the endpoint's slot); with no candidate left, `key_retired` is retryable on the existing reconnect backoff rather than terminal. A rotation the server declines (`rotation_pending`, `rotation_blocked`, `rotation_refused`) drops the pending key.
- A `command` frame is answered on the session loop. `openLedger` keeps `{outcome, detail, finished}` per command ID in the identity volume, so a command re-sent after a restart returns the answer already given rather than running twice: the server re-dispatches precisely when it never heard the first answer. The ledger is bounded both ways (24 hours, 10,000 entries, oldest trimmed first). A command addressed to another endpoint, or past its deadline, is refused without touching the runtime and without being remembered, since there is nothing to be idempotent about.
- `Auth` names the fingerprint of the signing key, so the server can say `key_retired` or `key_pending_review` instead of a bare refusal.
- Inventory: `Options.Snapshot` (the Docker adapter in `cmd/agent`, `--docker-socket`, empty disables) is read at connect and every `--inventory-every` (default 60 s) and sent as a `protocol.Snapshot` under a generation that rises across restarts; when the runtime is unreachable a facts-only snapshot is sent instead so the endpoint still reads as active.
- `protocol.Container.Mounts` (`mounts`: `{kind: volume|bind|other, source, target, read_only}`, source the volume name or host path) is `nil` when the agent did not report mounts (older than the field) and `[]` when there are none, so the field has no `omitempty`. `Container.UnmarshalJSON` decodes at most `MaxMounts` (32) and sets `MountsTruncated` for the rest, on every decode path; `Clamp` caps and cleans them (a source or target changed by cleaning or the 512-byte cut also sets `MountsTruncated`) and maps unknown kinds to `other` without inventing a list; `Shrink` drops every container's mounts (marking each truncated) after labels and before any list tail.
- `Run` reconnects with 1 s → 60 s exponential backoff and ±20 % jitter, heartbeats at the interval the server states (capped below 60 s so nginx defaults hold), sends one inventory snapshot per session with a generation that rises across restarts (`Identity.Generation`, persisted through `Options.IdentityDir`, incremented only from the persisted counter), bounds the handshake to 15 s and every later read to two heartbeat intervals so a silent path triggers a reconnect, reconnects on `enrollment.approved`, and stops on `identity_revoked`/`enrollment_rejected` or an incompatible version. Cancelling the context closes the socket with `agent_shutdown`.
- After each inventory snapshot, `Options.Metrics` (the adapter's `Stats`) samples the snapshot's running containers in a goroutine, reading each one's restart counter from container inspect in the same per-container budget (the stats endpoint does not carry it; a refusal is -1, not zero), and hands the frame back to the loop through a one-slot channel, so a slow daemon never starves heartbeats; the agent shrinks metrics to `protocol.MaxMetricsBytes` before sending, a frame with no samples is not sent, and a frame is dropped if the previous one is still waiting.

- Exec opens bind stream, actor, endpoint, immutable target, explicit user and dimensions to the authenticated connection nonce, with at most 60 seconds to start. Consumed grants remain until expiry (1,024-entry ceiling, no live-grant eviction); replay or invalid scope ends the socket. At most four workers per endpoint and one per actor run, with admission owned by `Run` across reconnects and released only after runtime workers finish. Pending agents refuse exec. An active agent without an exec adapter consumes the grant and answers `exec.close` with an unavailable-runtime reason, preserving the connection and heartbeats.
- Terminal chunks preserve raw bytes through base64 JSON (32 KiB decoded, 64 KiB payload). Each stream queues eight input/resize frames; overflow cancels its attachment. Output shares the eight-frame session queue, applies backpressure off the socket loop, and closes the attachment after a five-second queue stall. Close follows queued output on the same FIFO. Cancellation/disconnect closes runtime I/O; EOF produces an exit code only after successful runtime inspection. No runtime error text, argv or terminal data is logged. An attachment close never promises process termination.

## Child DOX Index
None.

- Log streams are session state, unlike commands: the reader waiting for the chunks is an HTTP request the control plane holds open on this same socket, so a stream that outlived the session would be reading the host for nobody. At most `protocol.MaxLogStreamsPerEndpoint` run at once -- the protocol's number rather than one of the agent's own, because the control plane hands out places against the same limit and splits them per reader -- and a chunk that cannot be queued for the session loop is dropped and counted rather than held, because the loop that would be blocked also carries the heartbeats. The count travels with the next chunk, so the reader is told where the hole is. A read is coerced to valid UTF-8 and then split to `protocol.MaxLogChunkBytes` on character boundaries: coercion grows the text -- one multi-byte character straddling a read boundary is enough -- and the bound the protocol states is on what travels, not on what was read.
